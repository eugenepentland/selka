# Remaining schematic algorithm and representation costs

This review uses the indexed guest source and the `mylang-o3` objects recorded in its QBE manifest. The qualified fixture has 30 parts, 99 pins (95 connected and 4 NC), 34 display nets, 37 connected hub pins, and 29 two-pin passives. This deliberately excludes the host-call issues removed by `circuit.normalize` and does not reuse claims from the pre-index audit.

## Ranked findings

1. **Passive placement repeatedly recomputes topology with whole-list scans.** `layout.build` calls `endpoint` for each of the 58 passive pins (`layout.my:372-393`). Each endpoint calls `innerPin`, `nearest`, `bridge`, and `branch` (`315-359`). `innerPin` performs two `partPin` scans of all 99 pins (`191-226`); `endpoint` then scans all 30 parts and invokes `innerPin` and `bridge` again (`338-346`). `branch` scans all parts twice and recursively follows predecessor branches (`267-312`); within those scans, `innerPin`, `bridge`, and `groundBranch` repeat part/pin scans. The cached `Part.pin1/pin2` indices are used in `layout_graph.build` but not in these layout helpers. This is the strongest remaining algorithmic multiplier: a single passive endpoint causes several 30-part scans, many 99-pin scans, and potentially recursive repeats. Replace `partPin` with the cached part pin indices, then precompute per-part inner/outer pin, depth, owner row, bridge, ground-branch class, branch predecessor, rank, and attached count once. Preserve source order when building rank/predecessor tables to retain ties.

2. **Hub row collection uses fixed-range nested scans.** `collectRows` scans all 99 pins for each number 1..128 (`layout.my:64-94`), a guaranteed 12,672 pin visits before its inner work. For each newly encountered group it scans member numbers 1..128 and all pins again (`77-92`), and each emitted row calls `rowHeight`. `rowHeight` scans all pins, then for matching passive pins scans all pins twice more (`32-58`). Build ordered hub-pin indices once by pin number and group, keeping the current number-major/source-order sequence, and compute row heights from net-to-pins and part pin indices. This removes fixed 128×N and nested N scans without changing ordering.

3. **Normalization remains quadratic and still performs textual comparisons, although only once.** `circuit.normalize` assigns raw identities by scanning prior pins and assigns display identities with a full 99-pin scan plus prior-display scan (`circuit.my:254-290`). On this fixture those loop bounds permit 4,851 prior-pin raw comparisons, 9,801 raw-vs-display comparisons, and another 4,851 prior-display comparisons. Short-circuiting reduces actual text calls, but this remains a bounded startup cost. A stable intern table keyed by `(file,start,end)` plus content-aware lookup for aliases could make this near-linear; insertion order must define IDs so first-match behavior remains exact. Rank it below placement because normalization already eliminated repeated downstream host-byte reads.

4. **Routing still performs all-pairs nearest searches.** Every connected pin scans all 99 pins to count peers and choose its nearest earlier peer (`layout_routes.my:64-88`), about 9,405 candidate visits for 95 connected pins. Rail/ground first pins may make a second full scan (`89-101`). `blocked` also scans all pins per lane trial (`42-58`, `264-274`). A display-net-to-pin index can restrict nearest/count work to members of that net, and spatial buckets can reject blocked lanes. Member lists must remain source ordered and nearest comparison must remain strict `<` to preserve ties.

5. **Managed-list access copies large records through runtime helpers.** Guest expressions such as `pin = pins[i]`, `other = pins[j]`, and `row = rows[i]` lower to `myl_native_list_get`; mutations lower to list-set helpers. The O3 objects remain unusually large: `circuit::normalize` is 40,173 bytes/6,907 instructions, `layout_graph::build` 41,770/7,278, and `layout_routes::build` 42,787/8,405. Their static runtime access sites are respectively 37 get + 8 set, 37 get + 7 set, and 16 get + 14 append. Static sites are not dynamic counts, but the sites inside nested loops show repeated whole-record transfer and bounds/type handling. Prefer compact parallel scalar indexes for hot topology facts, or add borrowing/reference access in the compiler/runtime rather than copying `Pin`, `Net`, and `Segment` values on every lookup.

6. **Allocation/root bookkeeping exists but is coarse, not visibly per loop iteration.** Each allocating O3 function has one frame allocation/root mark at entry; list constructors/appends are the allocation sites. `layout_graph.build` creates two lists, `layout.build` one points list, `layout_routes.build` one segment list. SVG rendering issues many output calls but does not build an in-memory SVG string. The emitted objects do not show a safepoint/root-mark call at every loop backedge. Without phase GC data this evidence does not support ranking root traffic above the repeated scans and record accesses. Pre-sizing known lists (99 points, at most a small multiple of 99 segments, at most 34 nets) would still eliminate growth reallocations and root updates.

## Code-generation evidence

`codegen.json` records text size, instruction count, list helper call sites, and managed-frame/root sites for the current O3 objects. Call-site counts are static sites in emitted object code, not runtime frequencies. The three largest reviewed functions are generated as monolithic 40–43 KiB bodies, consistent with repeated checked list/record lowering and branch expansion rather than small tight loops.

## Recommended sequence

First use `Part.pin1/pin2` everywhere in layout and precompute immutable per-part facts. Then replace `collectRows` fixed-range scans with stable ordered indexes. Next add display-net member lists shared by row height and routing. Only after those algorithmic changes should representation work target borrowed list elements or structure-of-arrays hot fields. Stable source-order construction, strict nearest comparison, recursive predecessor choice, and current branch rank ordering are semantic constraints and need exact SVG plus changed-net/value qualification after each step.
