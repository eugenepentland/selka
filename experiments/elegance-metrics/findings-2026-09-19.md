# Does propagation cost predict what a change costs?

Status: result, revised 19 September 2026 after the review in
[research-testing-review-2026-09-19](../../docs/audits/research-testing-review-2026-09-19.md)
found five defects in the first version of this measurement. All five are repaired
in [`propagation.py`](propagation.py), each with a regression check in
`--selftest` (12 checks, all passing), and every number below is regenerated by
the repaired tool.

**The conclusion is unchanged and now rests on cleaner ground.** Propagation cost
does not predict what a change costs an agent, and at the design level it does not
robustly separate the three arms — where it does, it favours the control design.
What the repair changed is the size and the honesty of the evidence, not the
answer.

## What the review fixed

| Defect | Repair | Regression |
| --- | --- | --- |
| Index cache keyed by entry path and `main.my`'s mtime, so an edit to an imported module reused a stale graph | Key is the source closure (every `.my` file), the compiler identity and a schema version | Indexing twice calls the compiler once; editing `helper.my` calls it again |
| `without_uses_type` removed four kinds and was byte-identical to `calls_and_fields` | Every ablation removes only what it names; four distinct policies are reported | The two sets differ; the ablated set is exactly `{uses_type}` |
| Deleted modules vanished from change accounting | Both snapshots are indexed, both diff sides are read, deletions and renames are recorded, and impact uses the **pre-change** graph | A deleted module reports an old-side range; a modified module reports both sides |
| A node could count itself through recursion or a cycle, against an `n - 1` denominator | The diagonal is excluded in `reach` | Isolated, self-looping, mutually recursive, cyclic, empty and singleton graphs |
| Ranks pooled across tasks with unequal chain counts and chains treated as independent | Independent runs by default, chains separate, ranks reported both pooled and centred | The chain rows are excluded from the default correlation |

## Design level: the three frozen arms

| arm | nodes | edges | propagation cost | top-10 mean impact | nodes over 10% |
| --- | ---: | ---: | ---: | ---: | ---: |
| B (baseline) | 123 | 371 | 0.047 | 0.178 | 11 |
| P1 (representation) | 137 | 384 | 0.041 | **0.154** | 15 |
| P2 (generalised control) | 218 | 738 | **0.039** | 0.176 | 13 |

The mean says both redesigns are more modular than the baseline and the control
most of all — but P2 is the arm that measured *worst* in the experiment (pack
gain −56,753 corrected, against P1's −28,998). Two checks say the ranking is an
artifact:

- **The mean is diluted by node count.** P2 has 218 declarations to B's 123, most
  of them small leaves with a small impact. On the size-controlled measure — the
  mean impact of the ten most impactful nodes — P2's advantage disappears (0.176
  against B's 0.178) and the two measures disagree about which redesign leads:
  the mean says P2, the top-10 says P1.
- **The edge policy moves the number more than the design does.** With the four
  distinct ablations now reported honestly:

  | edge policy | B | P1 | P2 |
  | --- | ---: | ---: | ---: |
  | all dependency kinds | 0.047 | 0.041 | 0.039 |
  | without `uses_type` only | 0.047 | 0.041 | 0.039 |
  | calls only | 0.020 | 0.016 | **0.010** |
  | calls and field traffic | 0.043 | 0.037 | 0.036 |

  The arm *order* survives every policy, but the magnitude swings by up to 4×
  (P2: 0.010 to 0.039) on a definitional choice. `without_uses_type` changing
  nothing is itself a finding: in this corpus every `uses_type` edge coincides
  with another dependency kind, so that ablation is not an ablation.

## Change level: the 63 independent changes

Spearman rank correlation with the corrected token cost (`cost_v2_input_output`;
chains excluded — they are repeated measures, not repetitions). "Centred"
subtracts each task's mean rank; with nine independent runs in every task that is
arithmetically inert, which is why the pooled and centred columns agree. The
review's −0.139 → −0.211 shift came from its mixed set, where chain-bearing tasks
had twelve rows and others nine.

| signal | overall Pearson | within-task rank | within-task centred |
| --- | ---: | ---: | ---: |
| **blast radius, pre-change graph** | +0.333 | **−0.223** | −0.223 |
| blast radius, post-change graph | +0.196 | −0.214 | −0.214 |
| read surface | +0.101 | −0.005 | −0.005 |
| touched declarations | +0.292 | +0.006 | +0.006 |
| diff lines | +0.146 | −0.115 | −0.115 |
| files changed | +0.549 | +0.082 | +0.082 |
| `api-diff` breaking changes | −0.006 | −0.093 | −0.093 |
| session steps | +0.699 | **+0.568** | +0.568 |
| tool results showing a failure | +0.695 | **+0.547** | +0.547 |
| bytes returned by `read` | +0.627 | +0.314 | +0.314 |
| seconds in compiler calls | +0.569 | +0.302 | +0.302 |

The static architecture signals are the weakest of the set and, inside a task,
the blast radius points the wrong way under every repair: −0.214 to −0.223.
The session signals that beat it are near-tautological — steps and bytes read
*are* what a token bill is made of — and their role is only to show that the run
set contains a strong cost signal for the static metric to miss.

The measure is not broken, only uninformative: T6's dialect change touches 14
declarations and has the largest blast radius (0.19–0.20); T4's printer change
touches `render` and `short_list_max_width` and has the smallest (0.008); and
four runs touch no declaration at all — P1's already-solved T7. No run in the set
deleted a module, so that repair is exercised by the selftest rather than by the
corpus.

## What this means

- The review's first recommendation — validate the scorer before building on it —
  is what this is, and it fails validation. On this corpus MacCormack-style
  propagation cost is not a proxy for what a change costs an agent.
- Both warned failure modes are visible: **Goodhart before the fact** (adding
  leaf declarations lowers the mean without simplifying anything) and **fragile
  definitions** (the edge policy moves the number 4×, and one advertised ablation
  turns out to be a no-op).
- What survives is the plumbing: `mylang index-project` resolves a whole project's
  reference graph in about 0.14 s, so change-impact questions are cheap to ask.
  That is worth keeping for lane D and for change-impact probes, independent of
  whether it ever becomes a score.
- The review's own caution applies to the correlation table itself: nine runs per
  task cannot resolve an effect this size. These numbers bound what a graph proxy
  can explain; they do not settle how much design matters.
