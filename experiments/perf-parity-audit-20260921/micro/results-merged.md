## Notes

- Every Zig kernel takes its loop bound through `common.opaqueN`, a volatile load that always yields 1, so no kernel loop can be constant-folded away. The mylang side needs no such guard: neither backend folds these loops.
- Each timing sample is a fresh `taskset -c <cpu> <binary>` process with stdout to /dev/null, so every number carries about 1 ms of process start-up on both sides.
- mylang keeps its overflow, bounds and division checks in ReleaseFast. `zig-fast` (ReleaseFast) has none of them; `zig-safe` (ReleaseSafe) has them and is the closer semantic match.
- **intloop**: Matched: one `+`, one `*`, one `%` per iteration on both sides. mylang checks the add and the multiply for overflow; `zig-fast` does not, `zig-safe` does.
- **calls**: Not fully isolating. The `% 1000003` in the callee costs about as much as the call on both sides, so this kernel lands within noise of `intloop` for every arm: read the *difference* against `intloop`, not the absolute ratio.
- **calls**: The Zig callee is `noinline`; mylang has no inline control, so an LLVM arm may inline `step` where `zig-fast` cannot. `zig-fast-inline` is the same body without the barrier.
- **fib**: Matched: the same two-branch double recursion, 29,860,703 calls.
- **records**: Neither side forces `norm1` out of line, so both may inline it; this measures record construction plus by-value passing as the compiler chooses to lower them, not a guaranteed real call.
- **list_append_sum**: Matched shape, different memory managers: mylang grows a traced `list[int]`, Zig grows `std.ArrayList(i64)` over `std.heap.smp_allocator`. The fold is a `for` over the elements on both sides and LLVM may vectorise the Zig one.
- **list_records**: Matched: 2,000,000 four-field 32-byte records appended, then ten passes summing field `c`.
- **dict_count**: The primary `zig-fast` arm uses `get` + `put`, two hash lookups, to mirror mylang's `counts[key] = counts.get(key, 0) + 1`. `zig-fast-getorput` is the idiomatic single-lookup form and is the fairer picture of what Zig can do.
- **dict_count**: Keys are the same 1000 strings `key0`..`key999` on both sides, built before the timed loop.
- **dict_count**: Root cause, read off the runtime rather than inferred: `src/native_dictionary.c` stores a dictionary as a flat entry list and its `find()` walks every entry, comparing string keys one by one. A mylang `dict` is an association list with O(n) lookup, not a hash table, so this kernel is comparing an O(K) scan against an O(1) hash and the ratio grows with the key count.
- **str_build**: mylang appends through `byte_buffer.append_range(piece, 0, 8)`, Zig through `std.ArrayList(u8).appendSlice`. Same piece, same count, same final length; the sampling fold at the end is identical.
- **alloc_churn**: Four different memory strategies, deliberately: `mylang-*` drops each batch on the tracing GC, `mylang-*-arena` opens `with arena():` per batch, `zig-fast` resets a `std.heap.ArenaAllocator` per batch over `page_allocator`, and `zig-fast-gpa` allocates and frees through `std.heap.smp_allocator`.
- **float_loop**: Matched: `x = x * 0.999 + sqrt(float(i))` in strict IEEE binary64 order on both sides, printed as `int(x * 1000.0)`. All arms agree byte for byte, so no FMA contraction or reassociation happened on either side.
- **bytes_scan**: Same algorithm, very different codegen: LLVM auto-vectorises the Zig index loop, while mylang reads one bounds-checked octet at a time. The gap is a vectorisation gap, not an algorithmic one.
