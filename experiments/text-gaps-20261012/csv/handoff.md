The concrete first bottleneck was the first consuming append to an immortal text prefix: the owned runtime copied the prefix into an intermediate owner and immediately grew that owner into another allocation. Large csv_rows performed 1,280 empty-prefix copies and 1,280 growths per job. The new path allocates the final append owner directly. It neither modifies nor frees the static prefix, captures aliased scalar octets before allocation/free, and retains independent snapshot and escaped owner behavior. Signed length addition, capacity doubling and native size/rounding checks precede allocation and prefix copying. RC retains its existing ownership path. Existing append/growth counter anchors remain unique; the removed intermediate copy and allocation are absent from counters.

Trial 02 tested moving the already checked character width computation earlier in the loop. Its five-round screen regressed relative to trial 01 (large 61.313 µs, small 3.683 µs), so the compiler transformation and its structural tests were completely reverted. The exact discarded patch remains in trial02/source.patch for ablation.

Trial 03 forces the internal append implementation into its two wrappers only in zero-RC builds. Machine code previously called append_bytes from append_char for every scalar, keeping a stack capture across that nested call. Inlining removes that nested call. Its five-round large screen measured 54.147 µs versus baseline 67.654 µs and Zig Fast 52.577 µs, ratio 1.030. This exploratory screen remains above the target; the small result is pending.

Trial 04 tests an isolated ASCII character append arm when a mutable destination has ordinary spare capacity. It captures the source octet before writing and invokes the same inlined append implementation, preserving counter anchors, terminator and cached hash/scalar invalidation. Checked scalar width still validates offset/UTF-8; Unicode, static, cursor and growth cases retain the general path. It has no new ABI or compiler proof.
