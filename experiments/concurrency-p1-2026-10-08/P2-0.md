# P2-0: existing Core IR supports the task surface

This is a read-only analysis of the current compiler. P2 is not authorized by this report: its start still needs the front-end plan's F4 exit and the user's go. The integrated hand-built proofs pass at `9f911528f` at 1, 2 and 8 threads, including real emitted LLVM under ThreadSanitizer. P1’s final repetition/gate results are recorded separately in REPORT.md.

## Existing Core IR is sufficient

The proposed surface needs new checking and lowering, not a new Core operation. Today's IR already supplies typed `func_ref`, ordinary helper `call` with `.runtime_c` linkage, records, `box_make`/`box_get`, lists, loops and phis. `src/core/test_builder.zig` provides SSA construction and runtime helper declarations. `src/core/build_host.zig` already demonstrates boxing an argument record around a helper call; `build_values.zig` and `build_render.zig` use the same representation pattern. `src/core/build_fn.zig` maps noncapturing callable signatures and recognizes function references. The existing ownership pass borrows ordinary call arguments and owns managed call results. Its `shared` analysis (`own.zig:762`) explicitly treats a call as potentially retaining its argument, even at the value’s last use; `exclusiveChildren` also rejects child values lent to calls. This is why asynchronous retention through the task ABI does not require weakening a static-uniqueness proof. `promote.zig` likewise treats values passed to calls or capture containers as escaping, so the environments cannot contain stack-promoted lists.

P1's native task/group kinds do not need corresponding IR type tags. The builder gives their handles opaque managed box representations and never emits `box_get` on a handle. Their runtime headers carry the actual kind and child layout. The value returned by `task_result` is the thunk's genuine result box and is the only object unboxed for the user. A handle's internal payload is not a source record.

| Surface construct | Existing-IR lowering | Ownership/lifetime |
|---|---|---|
| `with parallel.group() as g` | `.runtime_c` call to `myl_core_group_open()` returning a managed opaque handle | Result is +1; add its close operation to structured scope exits, then release the handle normally |
| `g.submit(fn, args...)` | Evaluate arguments; make a record; `box_make`; typed `func_ref` of a generated `run(env)->box[R]`; call `myl_core_task_submit(g, run, env, -1)` | Arguments are borrowed; multi-thread runtime shares/retains the environment before publication; at one thread it runs immediately without that retain/share |
| Generated task thunk | `box_get` environment; field projections; direct or indirect typed call to the original function; `box_make` its result; return | Existing ownership inserts the retained children needed by the result; runtime releases the task environment after invocation |
| `t.result()` | Call `myl_core_task_result(t)` then `box_get` | Each helper result is +1; the original handle retains its result for repeated reads |
| Scope exit | Call `myl_core_group_close(g)` on fallthrough, return, break, continue and propagated failure | Close waits while running available work; handles remain valid after the group scope |
| `parallel.map(fn, items, context...)` | Compute `k=map_chunks(len(items))`; on multiple threads share items/context once; build contiguous range environments; submit generated range-loop thunks; gather chunk results in input order into one list | Per-range result lists are owned; appended managed elements retain or transfer ownership under existing list operations; internal handle collections do not escape to source code |
| Nested groups/maps | The same helper sequence inside the thunk | Worker-local submit and waiting support nested work without a separate scheduler interface |

Use `start = i*n/k`, `end = (i+1)*n/k`, with overflow-safe arithmetic or quotient/remainder partitioning in the actual builder. Empty input returns an empty list without dividing by zero or starting workers. `map_chunks(0)` returns 0; one thread yields one range for nonempty input and source item order. A `Result` return is an ordinary element of `list[Result[R,E]]`, not a scheduler error. Zero-argument submit uses an empty environment record; a void-returning task can box an empty result record if the existing box mapping does not admit void directly. These are representation choices, not new IR operations.

The thunk pointer uses `fastcc`. C must call it only through P1's emitted C-ABI `myl_core_task_call` bridge, which invokes `call fastcc ptr %run(ptr %env)`. P1 uses `weak_odr hidden`: it survives optimization when only the separately compiled C runtime calls it and deduplicates across units. `func_ref` makes the thunk address visible to existing partitioning and reachability code (`emit_units.zig`); it must not be removed as an otherwise-unused function.

## Sites and errors

Group open and submit capture their C return addresses. Put the original source span on each emitted helper call; the return-PC DWARF lookup then identifies the submit/group site without adding ABI site parameters. Range tasks pass their starting item index and call the internal `myl_core_task_item(cursor)` helper before each loop body, so a later item reports its own index. A plain submit passes −1. The scheduler saves/restores task context, including that cursor, around nested work. The required fallback when no guest line information is available is `in task submitted at <unknown>`. Phase-1 returned-error traces start at the caller's `.result()` propagation; transporting a worker's trace is later work.

Fatal errors still terminate the process with status 1. They do not become `Result` values. Task-side output is one complete print/write/debug unit at a time; output order between tasks is unspecified, while one-thread execution retains sequential order. No provider operation or Host cleanup is entered on the fatal multi-thread path.

`build.zig` currently lowers `.with_scope` at line 723 and maintains resource scope depths. `build_cap.closeScopes` closes crossed scopes in reverse order. `returnValue` invokes it for returns; propagated `?` failures also call `returnValue`; loop exits call it with their target depth. Generalize the close-operation record so file and group scopes share those existing exit paths. Do not introduce a separate partial exit mechanism that omits `?`, break or continue.

Handle checking needs a whole-function assignment/use inventory before ordinary lowering: E_TASK_HANDLE concerns assignment anywhere in the function, and E_TASK_RESULT_UNREAD is syntactic use across branches rather than waiting until runtime. Generated map handle lists are compiler implementation storage, not permission for user handles to enter collections.

The current callable schema is immediate scalar storage with no captured state (`callables.intern`), and its signature contains mutates/effect data. Reuse this rather than allowing capturing closures as a special task case. Resource/Host containment must distinguish owned handles from capabilities: `typed.resourceKind` recognizes direct resources, but nested lists, dictionaries, records and unions need a recursive walk. Existing data-type admissibility rejects more than the task rule, so it cannot be substituted wholesale.

## Proof and remaining integration risks

[`task_ir_program.zig`](../../src/core/task_ir_program.zig) supplies two hand-built programs: mixed list/record/dictionary/string/nested-list captures returning retained shared children, and a map-shaped range thunk with explicit loops/phis and ordered gathering. [`task_ir_test.zig`](../../src/core/task_ir_test.zig) verifies them after the real ownership pass and LLVM emitter, through the real native linker and runtime.

The mixed-capture program appends to the parent list after submission: the parent prints length **4**, while each of eight task results retains the original length **3**, allocated string **keyé**, and sum **60**. Each result is read twice; counted/verified execution reports zero live bytes. The range proof gathers **100 through 131 in order** at 1/2/8 threads, with shared item storage before parallel submission. A second range proof traps on **item 17** even when a multi-item range began at 16, and reports the original source line. Submission-PC and no-DWARF fallback tests also pass.

The integrated checkpoint passes **11/11 tests** ([recorded log](r3/loose-logs.tar.xz)), including Debug, Release/ownership verification, counted captures, actual LLVM TSan captures/ranges at 1/2/8 threads, native scheduler TSan, cache separation, and instrumentation-attribute validation. The final 100-repetition result is separate package evidence, not a substitute for this lowering proof.


The IR vocabulary has no identified gap. The main P2 risks are checker confinement, all-exit close lowering, generated thunk reachability, overflow-safe range boundaries, and CLI permit/stack accounting. If executable proof exposes a genuine IR or ownership-pass gap, the P1 hard-stop rule applies; do not edit ir.zig or own.zig to hide it.
