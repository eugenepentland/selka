# Diagnostic feedback: does better feedback make agents repair faster?

Status: result, 19 September 2026. Experiment 1 of the review's list in
[research-testing-review-2026-09-19](../../docs/audits/research-testing-review-2026-09-19.md).

**Answer: it depends on the family, and the loop is worth its budget.** On faults
whose message names a concept but not the remedy, a fix-carrying diagnostic cut
median repair rounds from 4 to 1. On the invocation family it changed nothing —
and that is exactly the family where one-shot generation fails. Plain structured
JSON showed no benefit. One repair session beat one independent sample on both
solve rate and output tokens.

## What ran

96 sessions: 8 held-out faults × 4 conditions × 3 runs, in randomized order
(seed 20260919), plus 12 re-runs of one fault after the pilot caught a defect in
it. Every session is a fresh `dsh --profile headless` agent in a working copy
holding only the faulty project, the request, and `bin/mylang` — which in this
experiment is a wrapper around the frozen compiler and the *only* difference
between conditions:

| condition | what the agent sees |
| --- | --- |
| `text` | the checker's own output, unchanged |
| `structured` | each diagnostic as one JSON object (`code`, `message`, `path`, `line`, `column`, `snippet`, `notes`) |
| `fix` | the same JSON plus a `suggested_fix` naming a concrete alternative |
| `oneshot` | the text output, with a prompt allowing a single attempt — the equal-budget independent-sampling control |

The fix rules were authored against the `dev` half of the corpus and evaluated on
the held-out `test` half. Manipulation check: 24/24 structured sessions and 24/24
fix sessions actually received the intended output.

## Results

Cache-independent outcomes only — see the measurement note below.

| condition | n | solved | rate | median steps | median output tokens | median repair rounds | repeated errors |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| text | 24 | 24 | 1.00 | 8.5 | 1,398 | 2.5 | 24 |
| structured | 24 | 24 | 1.00 | 9.0 | 1,559 | 3.0 | 33 |
| fix | 24 | 24 | 1.00 | 8.0 | 1,371 | 1.5 | 17 |
| oneshot (control) | 24 | 19 | 0.79 | 6.0 | 4,668 | — | 21 |

Solve rate is at the ceiling for the three feedback conditions, so the
sensitivity is in the repair behaviour. Median rounds hide where the effect is;
per family:

| fault family | text | structured | fix |
| --- | ---: | ---: | ---: |
| checked-result (`expected int, found Result[…]`) | 4.0 | 7.0 | **1.0** |
| generic-requirement (`unknown requirement; expected …`) | 4.0 | 8.0 | **1.0** |
| bool/int (`expected int, found bool`) | 4.0 | 3.0 | 5.0 |
| module-name / module-path (invocation) | 3.0 | 3.0 | 3.0 |
| output-capability, variant-coverage, unknown-name | 1.0 | 1.0 | 1.0 |

Three things follow.

1. **A fix helps where the message names a concept but not the remedy.** For a
   `Result` returned where an `int` is expected, and for an unsupported generic
   requirement, the suggestion takes the median from four round trips to one.
2. **It does nothing for the invocation family.** `module-name` and `module-path`
   sit at 3.0 rounds in every condition, including `fix`, whose suggestion says
   exactly where the module header and the import path must point. That family is
   also where the one-shot control collapses (1/6 solved against 6/6 for every
   feedback condition).
3. **Structured JSON alone is not an improvement.** It is equal to plain text on
   five families and worse on the two the fix helps with (7.0 and 8.0 rounds). If
   anything in this data argues for structuring, it is that structuring makes the
   suggestion attachable — not that agents read JSON better than prose.

## Repair loop versus equal-budget resampling

The control answers the review's question directly. One one-shot attempt costs
**3.3× the output tokens** of a repair session (median 4,668 against 1,398) and
still solves less often (19/24 against 24/24). To match one repair session's
budget you would buy less than one independent sample, and independent samples
fail exactly on the invocation faults where feedback is what closes the gap. On
this corpus the loop is not a disguised way of buying more attempts; it is
cheaper per attempt *and* more reliable.

## Measurement notes

- **The pilot earned its keep.** One fault (`unknown-name`) was unsolvable in
  every condition — 0/12 — because the corpus pinned the wrong expected stdout
  (the request said `15`, the hidden manifest still said `10`). The pilot and the
  per-fault table caught it; 12 cells were re-run after the fix. Without that
  check the headline would have been a fake three-way tie on a broken task.
- **Token cost is dominated by prompt-cache warmth at this session length.** The
  same fault, the same 5–8 steps and the same bytes read cost 10,500–11,300
  *uncached* input tokens in one sitting and 1,300–2,300 in another, with cache
  reads correspondingly higher. `input + output` therefore measures when a
  session ran, not what it did. Output tokens, steps and repair rounds are stable
  and are what the tables above use; the run records keep every raw field so a
  different normalization can be applied later.
- **The faults are small**, so solve rate is at the ceiling for any condition that
  can run the checker. Detecting a solve-rate effect needs harder or multi-error
  faults; detecting a repair-round effect needs more runs per cell than three.

## What to do next

1. **More runs on the responsive families**, not on all eight: `checked-result`
   and `generic-requirement` are where the effect is, and a 10-run-per-cell
   comparison there costs about the same as the whole study did.
2. **Attack the invocation family separately.** Every condition sat at 3.0 rounds
   there, and the fix text was ignored; the useful experiment is a *stronger*
   intervention (for example a wrapper that refuses to run a test module as a
   program and says which command to use) rather than better wording.
3. **Harder faults** to lift the solve-rate ceiling: two seeded errors, or a fault
   whose fix requires a type or effect change across two functions.
4. **Re-run the loop-versus-resampling comparison at matched token budgets**
   rather than matched attempts: k one-shot samples per repair session, using the
   measured output-token ratio, and compare solve rates at equal spend.
