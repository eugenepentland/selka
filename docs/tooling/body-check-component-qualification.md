# Body component qualification

The B5 `body-check` package owns checking and producing complete typed bodies for ordinary nongeneric functions using `int` (i64), `bool`, `Unit`, `str`, `bytes`, and supported lists and ordinary nongeneric records, unboxed enums/unions and checked Result/Option values whose payloads use admitted types. Record recursion through lists is supported. The retained native catalog supplies canonical identities; Selka supplies ordered tagged recipes for new list, Result and Option types. Entry policy, effect/origin analysis, and warnings remain separate. Other collections, generic/boxed records or variants, generics, callbacks/lambdas, resources, and unimplemented operations remain explicit profile refusals. They must never silently fall back to native body checking. Native reference remains the default.

`MYLANG_BODY_CHECK_MODE=reference|shadow|component` selects this boundary. Shadow compares the entire canonical typed batch, ordered diagnostics, import usage and ordered catalog recipes. Native checking runs against its untouched initial catalog. After outcome comparison, a separate fresh catalog materializes the producer recipes and compares every resulting record field with the native final catalog. The `dump-typed` and `dump-ir` comparisons in the installed harness supplement those comparisons; their textual output is not a complete typed metadata oracle.

The installed driver is `selfhost/tests/run_body_check_qualification.py`. It authenticates all seven packages, verifies the frozen seed through the native coordinator, and runs with an empty PATH. Python is developer orchestration only. The installed host and authenticated producer execute without Python.

The fixture manifest accounts separately for scalar/managed/list/record success, source diagnostics, and explicit profile refusals. It covers scalar calls/operators/control flow, imported body edits, executable and library checking, build/run/test behavior, ordered independent body errors, native warning publication, and Unicode byte locations. Private aliases referencing imported public scalar types preserve signature import usage and run successfully. Private imported calls preserve related dependency spans; nongeneric explicit type arguments, named-only calls, and mutable argument markers preserve diagnostics and repairs. Valid named-only and mutable writeback calls also run the generated program and compare its result. Signed i64 minimum/maximum and literal overflow, repeated default arguments, reversed named arguments, nested loop exits, forward/self/mutual recursion, and augmented assignment metadata and floor-remainder semantics remain permanent B1/B2 cases. Scalar `/=` and unknown-target augmented assignments preserve their native source diagnostics. Successful behavior fixtures run the generated program; all other scalar successes compare typed and lowered output. The original eight native-valid refusal fixtures cover generics, lambdas, float division, chained comparisons, explicit range stride, non-i64 integer suffixes, text methods and text repetition. The former list refusal fixture is now a required success. Assigning a readonly range variable remains an exact native `E_IMMUTABLE` source diagnostic. Three mixed workflows select all five frontend boundaries together. No compiler-component entry source is claimed to fit this profile.
