# Development velocity improvement loop

Started 2026-09-08. This continues the 53 recorded code-writing attempts across
11 task definitions. Existing evidence is immutable. The objective is to measure
and reduce `.selka` application delivery time to Python's on a broader, declared
workload without weakening correctness, memory safety, or verification.

## Work and evidence

1. Add twelve executable task definitions across text/data processing,
   configuration, stateful collections, binary codecs, paths and multi-module
   maintenance. Include new features and seeded bug repairs. Keep eight earlier
   application tasks and three owner-maintenance stages as historical references.
2. Implement missing general-purpose standard-library facilities before timing.
   Record the parity audit, preparation time, compiler/stdlib identities, starter
   sources, public tests, private-pack hashes, and verification policy. Never put
   a task's solution into a library helper or count library construction as an
   application attempt. Contract changes create a new task version.
3. Add observed operation timelines, source-change receipts, diagnostic histories,
   compiler/VM phase records and reproducible per-attempt reports. Preserve raw
   output; bound feedback separately. Label participant-declared activity and
   inferred command classifications distinctly from measurements. Unobserved
   time remains unknown, never renamed model reasoning or token generation.
4. Freeze tools and cases, then run fresh matched `.selka`/Python participants with
   the same public examples, hidden expectations, command limits, application
   clocks and testing workload. Preparation and private grading stay outside
   clocks. Start clocks before the coordinator hands off the task, consistently
   in both languages. Record dispatch gaps and concurrent host observations.
5. Grade every sealed attempt and review sources. Count failures, abandoned runs,
   deadline censoring and infrastructure problems; never discard a slow attempt.
   Diagnose the largest measured costs and recurring compile/ownership/API errors.
6. Pick a specific improvement supported by those diagnostics, implement and
   regression-test it, freeze a new iteration, and repeat matched development.
   Separate language/library changes from workflow changes where practical.
7. Check the predeclared Python-speed criterion on fresh confirmation cohorts.
   Report per-family regressions and preparation cost alongside aggregate speed.
   Speed parity on this corpus does not establish parity on all software work.

## Initial operating rules

Use inherited agent settings consistently; exact serving model, tokens and cost
remain null unless actual telemetry is available. No alternative model choice or
API billing is needed. Timed participants receive public materials only and do
not see other attempts, private tests, proposed solutions or performance results.
Command isolation uses the established namespace gateway; whole-agent access is
instruction-confined, and that limitation remains in every report.

The first pass is calibration, not proof of parity. Freeze a confirmation rule
before its first run; repeating exploratory trials until one looks favorable is
insufficient. Keep every iteration in a hash-chained journal and publish reports
to new paths. A restart must retain the interrupted attempt and record its cause.
