## What changed

### `list.sort()` — `src/native_collections.c`

The old sort was a generic bottom-up merge: an `n`-element `malloc` buffer, a
size/order switch on every comparison and `copy_element` on every move. It is
now an adaptive stable merge, shaped like CPython's listsort without galloping:

- Natural runs are kept, and strictly descending runs are reversed. Only strict
  runs are reversed, so equal elements cannot pass each other. A run shorter
  than the minimum run length (16–32 elements) is extended by stable insertion.
- Runs merge in powersort order through one scratch buffer of at most `n/2`
  elements. Each merge first skips the prefix and suffix that are already in
  place, then runs forward or backward depending on which side is shorter.
- The algorithm is written once over a `sort_kind`. `i64`, `u64`, `f64` and
  `str` each have an entry that passes a constant kind, so after inlining every
  comparison and move is specific to its type. For 8-byte kinds, the merge loads
  the next element of each side before the comparison. Advancing is then a pair
  of selects, not a load that waits for the comparison. The narrower integers
  share one generic entry that keeps the old per-comparison width switch.

In a standalone harness (2M random `i64`, `zig cc -O2`, the same load), the sort
alone went from 240 ms to 120–145 ms. The speculative-load merge loop accounts
for about 15% of that gain over the first rewrite. The minimum run length (16,
32 or 64) made no measurable difference.

The order is unchanged:

- integers by value;
- NaNs after every ordered float;
- signed zeros and equal values in input order;
- `str` by Unicode scalar value (bytewise UTF-8 through
  `myl_native_text_compare`).

A sort allocates nothing managed, so no collection can run while text pointers
sit in the scratch buffer. Identity, length, capacity and generation are
untouched, as before.

### `sort.sort_by_key` — `src/stdlib/sort.my`

The old recursive merge copied both halves and built a fresh output list at
every level. It also called the key twice per comparison, and it peaked at
225 MB for 16 MB of data. It is now a decorated sort over the integer path:

1. Every key is computed exactly once (`keys_in_merge_order`).
2. When every `key - min` fits above `bits = ceil(log2 n)` position bits in a
   63-bit word, the key list is rewritten in place to `(key - min) << bits |
   position` and sorted by `list[int].sort()`. The words are distinct, so their
   order is the stable key order.
3. When the keys are spread wider than `2^(63 - bits)`, it runs two such sorts:
   first by the low 32 key bits, then by the high 32 bits and the rank from the
   first pass.
4. One comprehension gathers `values[word & mask]` into the result.

A list longer than 2^31 elements has no room for a position beside 32 key bits,
so it keeps the old recursive merge. I did not forward to `sorted(key=)`: it
still calls the key twice per comparison (1.48× Zig), and its key-callback
lowering belongs to the crash-fix lane. Rewriting the keys in place instead of
building a second list of words cut the peak from 50.0 to 42.2 MB, at no
measurable cost in time.

**Trap order.** `docs/standard-library.md` promised that `sort_by_key` keeps its
"callback comparison and trap order". For a key function with no effects, the
only observable part of that promise is which trap fires first when several
elements would trap. Keys are deterministic, so the first trap comes from the
first *first-time* evaluation of a key. That order depends only on the shape of
the recursion: its halving ends in blocks of two or three elements, visited left
to right, each read from its last element to its first.

`keys_in_merge_order` walks exactly that order with an explicit stack, so the
reported trap is unchanged. `src/stdlib_sort_test.zig` tests this with a key
that overflows on one element and divides by zero on another. Keeping the order
costs about 10% of `sort_records`: a probe with plain input-order keys
(`[key(v) for v in values]`) ran at 0.905× of the shipped version over 15 paired
rounds. Wave 3's `list.sort(key=)` moves to Python's input order anyway, and
then this helper is a one-line swap.

### Two checker fixes the forwarding needed — `src/generic_bodies.zig`, `src/sema.zig`

- The abstract generic-body checker walks into every non-generic function that
  a generic function calls, and it rejected `values.sort()` there
  (`E_GENERIC_BODY_UNSUPPORTED`). No helper of `sort_by_key` could therefore
  reach the native sort. It now accepts `sort()` on a concrete `int`, `float` or
  `str` list and records it as a write to the receiver. A list whose element is
  a type parameter still rejects with `E_COLLECTION_METHOD`, and `pop` and the
  other unsupported operations are unchanged (GENERIC-BODY-3).
- The concrete checker rejected `list[str].sort()` ("sort requires an integer or
  float element type"), although PY-COLLECTIONS-15 promises `str`. Snapshot
  `a0cba3db` added `requireSortable`, which accepts `str`, and wired it in. A
  later merge put the old inline check back at both call sites and left
  `requireSortable` dead. Both sites call it again.

### Tests and spec

- SPEC bullets `LIST-SORT-RUNS-1`, `STANDARD-SORT-KEY-1` and `GENERIC-BODY-3`.
  `STANDARD-SORT-1`'s keyed clause now points at the new bullet, and
  `docs/standard-library.md` and `docs/python-syntax.md` describe the new
  engine.
- `tests/lang/stable_sorting.my` holds 13 guest tests:
  - every input shape at lengths around the run and merge thresholds, against
    an insertion reference;
  - long lists, against a linear oracle;
  - NaNs and signed zeros across merges;
  - multibyte text, checked scalar by scalar;
  - the `i8`–`u32` widths, and `u64` values above the signed range;
  - in-place `str` sort;
  - `sort_by_key` stability at every length, with keys spanning the whole `i64`
    range (the two-pass path), and with spans on both sides of the one-word
    limit.

  Each test stays under the runner's default of 1M steps (the largest uses
  0.85M).
- `src/stdlib_sort_test.zig` tests the trap order, and `sort_by_key` over records
  that hold `str` under `--gc-stress`. `src/generic_bodies_test.zig` tests
  GENERIC-BODY-3.
- `tests/native_collections_test.c` adds a differential test against insertion
  references for `i64`, `str` (stability checked by object identity) and `f64`
  (signed zeros). `scripts/test_native_memory.py` runs it, and it passes with
  UBSan and with ASan.
