# Inline allocation and a generational collector — 2026-09-22

Wave 4, items 6.5 and 6.6 of [the parity plan](performance-parity-plan-2026-09-22.md)
(§4.6, §6.5, §6.6, §7 wave 4). Branch `perf/alloc-gc` from `base/parity-w4`
(`0804a4cf`).

**Status: done, gated.** `binary_trees` now runs at **0.89× Zig** on the
collecting heap (it was 2.26× on the same run) and at **1.09× Zig** in an arena
(it was 1.41×). Against the base compiler the collecting program takes 0.40× the
CPU time and the arena program 0.78×. The collector's share of `binary_trees`
samples fell from 71% (allocation 32%, `trace` 20%, `heap_collect` 19%) to
13.6% on the plan's non-LTO profile build and 15.2% on the shipped LTO build.
Peak RSS of `binary_trees` fell from 53.8 MB to 33.0 MB and of `text_ops` from
64.4 MB to 34.8 MB. No other suite program moved beyond noise, apart from
`text_ops` (0.94×), `knucleotide` (0.96×) and `matmul_tuned` (0.84×), which got
faster. All numbers are from a loaded machine (load average 5–13), pinned to
CPU 2.

The acceptance targets: `binary_trees` ≤ 1.5× Zig — met (0.89×); ≤ 1.15× in an
arena — met (1.09×); trace + collect ≤ 15% of samples — met on the plan's
profile build (13.6%), at the line on the LTO build (15.2%); peak RSS ≤ 1.5×
Zig across the suite — not met, and not reachable by the collector alone (see
the RSS column and *What is left*).

## What changed

Five changes, each needed by the next.

### 1. Charges round to 16 bytes, not 32 (`GC-SEGMENT-1`)

`round_stride` rounded every charge up to `sizeof(max_align_t)`, which is 32
on x86-64, not to the payload's 16-byte alignment. Every charge was a
multiple of 32, so the 48-, 80- and 112-byte classes were never used. A
`binary_trees` node (16-byte header, 32-byte payload) took a 64-byte slot, a
third more than it needs. The alignment the header's static assertion
already guarantees is `alignof(max_align_t)`; charges now round to that.

### 2. Inline allocation windows (`QBE-INLINE-ALLOC-1`)

A `class` constructor whose body plus header fits a class of at most 256
bytes no longer calls the runtime. The heap carries, at a frozen offset
(`MYL_NATIVE_HEAP_INLINE_OFFSET`, asserted in C and mirrored in
`src/qbe_alloc.zig`), one `{cursor, limit}` window per inline class. The
generated fast path is:

```text
cursor = window.cursor; next = cursor + stride
if next <= window.limit:           # an empty window is {0, 0}
    window.cursor = next
    header = {count 1 << 2, &T_body}
    zero the payload                # LLVM drops the stores the constructor shadows
else:
    push roots; p = myl_native_heap_alloc_small(heap, &T_body, class); pop roots
```

The slow call is the only safepoint, so root records are published on that
branch alone (the `inline_roots` protocol `inlineAppend` already uses).

**Budget and trigger accounting.** A window is *prepaid*: when
`myl_native_heap_alloc_small` opens it, every slot in it is charged to
`bytes`, `objects_live` and the collection trigger at once, and it admits only
as many slots as `min(limit − bytes, next_collection − gc_bytes)` allows. So
popping every prepaid slot crosses neither the budget nor the trigger, and the
inline path needs no counter at all. The slots nobody took are discharged:

- before any collection decision (`prepare` settles every window when an
  allocation is due, then re-checks),
- when an arena opens (`myl_native_region_begin` settles; the windows stay
  empty until the depth is 0 again),
- and by the recount after every collection (see 4).

So a collection, and the `R_MEMORY_BUDGET` refusal after a full collection,
happen exactly where charging one object at a time would put them.
`--gc-stress` never opens a window, so every allocation still takes the
runtime path and collects. An `escape` copy suspends collection and opens no
window either.

**Soundness of the uninitialized window.** A window's slots hold whatever
their previous owner left. The inline path writes both header words and zeroes
every payload word before the constructor's field stores, with no safepoint in
between, so the collector never sees a partly written object. A zeroed payload
is also what the old free-list pop produced, so padding and inactive variant
payloads read the same as before.

**The class table is a compile-time contract.** `inline_class_strides` in
`src/qbe_alloc.zig` must match the first twelve entries of `class_strides` in
`src/native_heap.c`. A Zig test parses the C table and compares, and
`myl_native_heap_alloc_small` checks the compiler's class against its own table
(one comparison each way) and aborts on a mismatch rather than hand out a slot
of the wrong stride.

**Arenas.** In a program that opens arenas, the slow branch first tries a
second window at `MYL_NATIVE_HEAP_ARENA_OFFSET`: the free tail of the innermost
arena's current chunk, plus that depth's precomputed one-element arena mark
word. Arena chunks are zero-filled, so this path does not clear the payload.
The window is opened by the runtime's own arena allocation at the innermost
depth (never while an escape copy lowers the depth, never under
`--gc-stress`), and every runtime operation that reads or extends a chunk's
used prefix — allocation at another depth, the collector's arena scan, bulk
release — first folds the window's progress back into the chunk
(`myl_native_arena_sync`). The arena scan now walks a chunk's used prefix by
header size instead of by allocation count, because generated allocations are
not counted. The runtime's own arena allocations bump the same window when it
is open.

### 3. Holes instead of free lists

Storage is handed out as bump windows over *holes*, runs of consecutive free
slots a sweep found. A sweep writes one hole header (`{end, next}`) into the
first slot of each run and touches nothing else. A class takes the next hole of
its current segment, then of the next segment with holes, then the never-used
tail of its bump segment, then a fresh segment; every segment storage comes
from is marked dirty. The runtime path keeps its own window per class, and a
refill hands the inline path a whole hole in O(1) instead of threading a
free list slot by slot (the first version of this lane did that and spent 13%
of `binary_trees` in it).

### 4. A sticky-mark generational collector (`GC-GENERATIONS-1`, `QBE-GEN-BARRIER-1`)

Survivors keep their mark and are old; allocations are young. A **minor**
collection marks only young objects — `mark` returns at an old object without
tracing it — and frees only unreachable young objects. Its extra roots are the
old objects that may reference a young one:

- **Every old object whose descriptor is traced and is not a `class` body.**
  Lists, dictionaries, element storage and byte views change inside the C
  runtime with no barrier (an append into old storage, list growth giving an
  old header young storage), so they are simply rescanned by every minor
  collection. The rescan set is appended as objects are marked and reset by a
  full collection; oversized objects are found on the segment list instead,
  because growing one may move it.
- **Every old `class` body the store barrier reported.** Generated
  descriptors for class bodies carry `.cell = 1`. The only way a program
  writes into an existing class body is a field update (`update_record` on a
  managed record — the same instruction the mutation analysis in
  `src/mutation.zig` names as the one receiver write into a class, and the same
  place the arena region barrier sits). Before such an update stores anything
  the collector traces, generated code loads the body's mark word and tests
  bit 0; for an old body it calls `myl_native_heap_remember`, which clears the
  bit and lists the body. A minor collection traces every listed body's payload
  and sets the bit again. Scalar-only updates run no barrier.

A **full** collection clears every mark and reclaims everything unreachable. It
runs when the old generation (the bytes the last collection kept) reaches twice
what the last full collection kept plus 4 MiB; whenever an allocation would
cross the byte budget (so a refusal always follows a full collection); after a
remembered-set, rescan-set or worklist reservation failed; and for
`myl_native_heap_collect`. Under `--gc-stress` minor and full collections
alternate, so both run at every allocation.

**Pacing.** The next collection runs once the young generation grows by
`max(4 MiB, live / 2)` (it was `2 × live + 4 MiB`). The first version compared
the whole heap, young included, against the full threshold; with a young
generation larger than the old one every collection became full. It compares
the old generation now.

**Soundness argument.** The invariant is: *outside a collection, an old object
that is neither in the rescan set nor remembered references only old objects.*

- After any collection every reachable object is marked, so every reachable
  object's children are marked too.
- A young object becomes old only by being marked, which traces it, so its
  children are marked in the same collection.
- An old object gains a reference only by a store. Stores into runtime
  structures reach objects that are rescanned; stores into class bodies run
  the barrier, which removes the body from the "unwatched old" set until the
  next collection traces it; initializing stores go into young objects.
- Growing an oversized block preserves its mark (`heap_extend`), so growth
  never makes an old object young.
- `myl_native_heap_release` clears the released slot's mark and descriptor, so
  a stale rescan or remembered entry is skipped; nothing reuses the slot before
  the next sweep folds it into a hole.
- A collection abandoned for lack of worklist memory clears every mark and
  forces the next collection to be full.

Old garbage survives minor collections until the next full one; that is the
usual generational trade and the reason for the full threshold.

### 5. Side mark bitmaps and word-at-a-time sweeping (`GC-OBJECT-1`, `GC-SEGMENT-1`)

With sticky marks the old generation must not be walked by a minor sweep, and
a full collection must not pay a pass over every header to clear marks. Size
classes up to 8 KiB now live in 64 KiB segments aligned to their size, carved
from 2 MiB `aligned_alloc` reservations, with one mark bit per 16-byte granule
at the head of the segment. An object finds its bit by masking its own
address. Larger classes and oversized objects keep the mark in the header,
tagged by a new `MYL_NATIVE_OBJECT_LARGE` bit (63, above any element count).
For a bitmap object, header bit 0 is only the "old" flag the barrier tests; the
drain sets it for every object it marks.

- Clearing marks for a full collection is a 512-byte `memset` per segment.
- A minor collection sweeps only dirty segments; a sweep reads the mark words,
  skips a word with no bit set whole, and writes a hole header only at the
  start of each run between live objects. The bytes and object counts are
  recounted from live counts per segment (clean segments keep theirs), which
  also discharges every prepaid window slot nobody used.
- The collector flattens each traced element descriptor into at most eight
  `{pointer offset, tag offset, tag}` slots on first use and scans payloads
  with one loop (a variant inside a variant keeps the recursive walk). This
  was worth little on its own (the marking is bound by cache misses) but costs
  nothing.

How the collector's work in `binary_trees` changed along the way, from a
runtime relinked with timers (non-LTO objects, one run each on the loaded
machine, so the milliseconds are indicative rather than exact):

| step | minor collections | minor mark ms | minor sweep ms | full collections | full clear ms | full mark ms | full sweep ms |
|---|---:|---:|---:|---:|---:|---:|---:|
| sticky marks, header mark bits, full sweeps of dirty segments | 145 | 72.9 | 62.8 | 11 | 24.6 | 67.6 | 27.7 |
| side mark bitmaps | 145 | 41.7 | 19.8 | 11 | 0.3 | 42.2 | 7.1 |
| word-skipping sweep, old-generation full trigger | 163 | 27.4 | 3.6 | 9 | 0.0 | 14.7 | 1.4 |

The remaining marking is almost all promotion: minor collections mark 2.1
million objects over the run (of about 15 million allocated), because a
depth-14 or depth-16 tree under construction when a minor collection runs is
live and becomes old. A larger young generation promotes less — with a 16 MiB
floor the minor collections marked 0.67 million objects and the collector took
about 18 ms in all — but peak RSS rises with it (32.6 MB at 4 MiB, 38.0 MB at
16 MiB, 50.4 MB at 32 MiB). The shipped floor is 4 MiB.

## What is left

- **Peak RSS.** The ≤ 1.5× Zig target needs fewer and smaller objects, not a
  different collector: niche `Option` (6.9, `binary_trees` nodes 48 → 32
  bytes), shared `str` slices (5.4, `knucleotide`, `text_ops`), and the stdlib
  merge's copies (`sort_records`). A smaller young generation trades time for
  RSS; the measurements above give the curve.
- **Premature promotion.** A young object reachable at a minor collection is
  promoted at once. Aging (survive two minor collections) would keep
  `binary_trees`' in-progress trees young, but an object promoted while a
  child it references stays young needs remembering, and I judged that
  machinery too risky for this lane. A larger young generation gets most of
  the same effect at an RSS cost.
- **`mark` reads every child's header** to learn whether it is an arena,
  immortal or large object before consulting a bitmap, so a minor collection
  still takes a cache miss per reference into the old generation. Classifying
  an address by its pool reservation would avoid it.
- **Barrier deduplication.** Consecutive stores into the same body between two
  safepoints need one barrier, not one each.
- **Conservative stack scanning (6.7)** was out of scope. `myl_qbe_root_mark`
  and `myl_qbe_heap` show up at 7.5% in the non-LTO profile only; LTO inlines
  them.
- **Fresh segments are zeroed with `memset`** when carved from a pool
  (3.6% of `binary_trees` samples, mostly first-touch page faults that would
  otherwise land on the first allocation).
- **Found on the way:** `SPEC.md` on this base (and on `main`) begins with
  the fragment `ython`: its first line is truncated. Not touched here.
