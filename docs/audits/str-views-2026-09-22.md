# Shared `str` slices (text views) — wave 3, lane `perf/str-views` — 2026-09-22

**Headline.** A slice, a `split`/`splitlines`/`split()` piece and a
`strip`/`lstrip`/`rstrip` result can now be a *view*. A view is a 32-byte header
that reads a range of another text's UTF-8 octets instead of copying them.
Nothing observable changed.

What it buys:

- **Long slices are O(1).** Walking a text by repeatedly slicing off its front
  (`rest = rest[end + 1:]`, the shape of a hand-written tokenizer or line
  reader) was quadratic. The new `lib/slice_walk` benchmark goes from **239× Zig
  to 2.7× Zig** (paired 0.011 of before), and its peak RSS from **93.4 MB to
  7.0 MB**.
- **Retention is bounded.** A piece is shared only when it is at least a quarter
  of the text that owns the octets, so a live view keeps at most four times its
  own octets reachable. A guest test keeps a 40-octet slice of each of 600
  one-MiB texts. Under an always-share rule (Go's) it exceeds its 512 MiB budget;
  under this rule it passes (§3).

What it does not buy:

- **The plan's targets for `knucleotide` and `text_ops` are missed, and views
  cannot meet them** (§4). Their pieces are 1–20 octets. A view is still one
  managed object per piece, and for a piece that short a copy is in the same
  size class and costs the same to allocate and collect. Peak memory is
  unchanged on all three programs.
- **Not quite free.** `scan_split` is 1.9% faster. `knucleotide` is 3.6% slower
  and `text_ops` 1.4% slower. A counterfactual build attributes the
  `knucleotide` cost to the view test in the octet accessor; two follow-up
  changes recovered about half of it (§4).

Branch `perf/str-views` from `base/parity-w3-str` (`996a89ec`). All timings are
from a **loaded machine**. Load average was 6–34 while measuring, with other
agents building and gating. Everything ran on CPU 8, with interleaved rounds and
paired ratios with 95% bootstrap intervals. Result JSONs are in
[`results/wave3/`](../../experiments/perf-parity-plan-20260922/results/wave3/)
(`str-views-*.json`).

## 1. Representation

`src/native_text.h`.

- **An owned text is unchanged.** It is `{length, bytes, flags, hash}` (24
  bytes) followed by its payload in the same managed block. Generated code still
  loads only `length` (offset 0) and `bytes` (offset 8), so no compiler file
  changed.
- **A view** (`myl_native_text_view`) is the same four words followed by one
  pointer, `owner`, to the owned text whose payload it reads.
  - It is 32 bytes, so it lands in the 48-byte size class. Flag bit 2
    (`MYL_TEXT_VIEW`) marks it.
  - The `hash` word holds the view's octet offset into its owner's payload,
    instead of a cached hash. A view's hash is therefore recomputed on each
    request.
  - The dictionary already keeps every stored key's hash in its index. It also
    stores view keys as owned copies (§2). So a view's hash is computed once per
    lookup, as a fresh copy's was.
- **One accessor.** `myl_native_text_storage(text)` returns `text + 1` for an
  owned text and `owner + 1 + offset` for a view.
  - Every runtime reader already goes through it: equality, order, hashing,
    search, `count`, `replace`, `split`, printing, f-strings, `int`/`float`,
    `encode`, byte-buffer appends, hex and the codec's scalar walk.
  - So does `myl_native_text_utf8`, which copies octets out for files, host
    paths and `mylang invoke`.
  - No consumer needed a change of its own. Builders write the freshly built
    owned text directly.
- **No chains.** A view of a view points at the first view's owner, with the
  offsets summed. Reading any text's octets is at most one hop, and no view
  keeps another view alive.
- **The collector did not change.** A view is allocated with an element
  descriptor (`myl_native_text_view_type`) that is an ordinary one-pointer
  record.
  - The tracing heap marks the owner through that descriptor.
  - The arena scan traces an arena view's outer owner the same way.
  - Nothing in `native_heap.c` or `native_arena.c` changed, so there is nothing
    to merge with `perf/alloc-gc`.
- **UTF-8 metadata.** A view carries its own scalar count and ASCII flag,
  computed from its own octets exactly as a copied piece's were. Scalar
  indexing, `len`, `find`'s scalar answer and `ord` are unchanged. A text has no
  other per-text cache.
- **`bytes` ↔ `str`.** Unchanged. `encode()` copies the octets out;
  `decode()`/`from_utf8` build an owned text. The existing byte-string views are
  a separate mechanism (list headers) and never become text views.
- **Host, wire and codec boundaries.** None of them sees a view. File paths,
  environment names, host/wire nodes and `mylang invoke` results already copy the
  octets into their own contiguous buffer. Nothing relied on a NUL after a
  payload.

## 2. Producers and consumers touched

All producers are in `src/native_text.c`. `native_text_methods.c` reaches them
through `myl_native_text_substring`.

| producer | before | now |
|---|---|---|
| `s[a:b]` (`myl_native_text_slice` → `copy`) | copy | view, copy, or `s` itself |
| `split(sep)` | copy per piece | same rule; the threshold is computed once per call |
| `splitlines()`, `split()` | copy per piece | same rule (via `substring`) |
| `strip`/`lstrip`/`rstrip` | copy | same rule; an already-stripped text answers itself |
| `zfill(w)` with nothing to pad | copy | the receiver itself |
| `text[i]` non-ASCII, stepped slices, `+`, `join`, `replace`, case mapping | copy | unchanged: a scalar is at most 4 octets, and the rest build new octets |

`partition`, `rfind`, `index` and a `maxsplit` argument do not exist on `str`
(checked against the method table), so nothing else needed converting.

**Whole receiver.** A piece equal to its whole receiver is the receiver itself,
but only when the receiver already lives in the innermost open arena.

- Inside `with arena()`, a whole-text piece of an outer text is still a new
  object in the arena (a view), as the copy was.
- So `R_ARENA_ESCAPE` traps exactly where it always did. This is tested in
  `src/arena_managed_test.zig`.

**Arenas.**

- Every view is allocated at the current depth, like every copy.
- Its owner is never younger: the owner already exists, and no live object is
  deeper than the innermost open arena. So the store barrier's one-hop reach
  stays exact. `shares` also checks this invariant directly.
- The escape copier needed no change. `myl_native_text_clone` copies a text's
  octets through the accessor, so an escaping view becomes an owned text of its
  own octets in the enclosing region.

**Dictionary** (`src/native_dictionary.c`, three small changes):

- `insert` stores a view key as an owned copy of its octets, allocated in the
  dictionary's own region by `myl_native_text_own_at`.
- `same_text` therefore reads a stored key's octets from its header's tail.
- `probe_text` resolves the queried text's octets once per walk, not once per
  comparison.

This keeps the accessor's test off the stored-key side of every comparison, and
it means no dictionary key can keep a larger text alive. No generated program can
insert an arena view into an outer dictionary: the store barrier traps first, as
it did for a copy.

**Budget.** A view is charged as the 48-byte object it is. A refused allocation
returns NULL exactly as a refused copy did, so the budget trap and its location
are unchanged. No path needs more memory than before: a view is made only for
pieces of at least 9 octets, and it is never larger than the copy it replaces.

## 3. Retention policy, and how it was chosen

```
count <  9                      → copy   (a copy of ≤ 8 octets is 48 bytes, like a view)
count ≥ owner.bytes / 4         → view   (a live view keeps ≤ 4× its octets reachable)
otherwise                       → copy
offset > 4 GiB                  → copy   (the offset lives in the 32-bit hash word)
```

The policy was chosen by measurement. A tuning build read both constants from
the environment; that code was removed before commit. It ran against the base
compiler on the four text programs, with 7–9 interleaved rounds per program
(`results/wave3/str-views-policy-*.json`, medians and peak RSS):

| program | never share | ratio 4 (chosen) | always share (Go) |
|---|---|---|---|
| `text_ops` | = base | = base | = base, same RSS |
| `scan_split` | 169.8 ms, 86.4 MB | 169.4 ms, 86.4 MB | **180.4 ms, 109.7 MB** |
| `knucleotide` | = base | = base (its keys are copies) | = base |
| `slice_walk` | 743 ms, 93.4 MB | **9.9 ms, 12.9 MB** | 8.1 ms, 12.9 MB |

A C harness over the real runtime gave the same picture. It ran `split("\n")` on
the 4 MB LIB text (220,000 pieces, best of 15):

- The cost was 67–69 ns per piece whether the pieces were copies (never share,
  ratio 4) or 220,000 views (always share).
- For 40–400-octet slices of a 4 MB text, a view took 61 ns per piece against a
  copy's 86 ns. The difference is the memcpy, which is the only per-piece saving
  a view has.

**Conclusion.** Sharing a short piece of a large text buys nothing measurable
and costs retention (and, in `scan_split`, 27% more peak memory). Every gain
comes from sharing a large fraction of the owner. The ratio rule keeps those
gains and bounds retention.

It also keeps the front-slicing walk linear. Once `rest` drops below a quarter
of its owner, the next piece is copied and becomes the new owner. The total
copied is a geometric series, at most a third of the text.

The retention test (`test_a_short_piece_does_not_keep_a_large_receiver_alive`)
discriminates between the rules. Under always-share it traps `R_MEMORY_BUDGET`;
under the chosen rule, and on the base compiler, it passes.

**Acceptance.**

| target | result | met? |
|---|---|---|
| `knucleotide` ≤ 1.5× Zig | 3.53× (before 3.39×) | **no** |
| `text_ops` ≤ 1.3× Zig | 4.16× (before 4.09×) | **no** |
| peak RSS ≤ 2× Zig on both | `knucleotide` 7.1×, `text_ops` 8.3× (both unchanged) | **no** |

**Why views cannot reach the targets.** Profiles are SIGPROF samples from
`prof.py` on `--keep-symbols` LTO builds of the base compiler.

- **`text_ops`.** Allocation and collection are half the samples:
  `heap_alloc_at` 17.4%, `heap_collect` 16.1%, `trace` 8.2%, `slot_take` 8.0%.
  Another 21% is libc: `memset` of reused slots, `calloc` of segments,
  `memcpy`.
  - The objects are the 200,000 lines, the 600,000 fields, the 200,000 field
    lists and the f-string temporaries.
  - The lines average 20 octets and the fields fewer than 11, out of a 4 MB
    text. Whether each piece is a 64-byte copy or a 48-byte view, it is one
    allocation, one slot to sweep and one object to mark.
  - Building the text alone already takes about 3× Zig's whole program (see the
    `lib-text-scan` report). So no change to the pieces can reach 1.3×.
- **`knucleotide`.** `probe_text` 29%, the guest loop 17%, `heap_alloc_at` 16%,
  `text_hash` 6%, `heap_collect` 7%.
  - Its keys are 1–18 octets of a 1 MB text. A copy is 48–64 bytes; a view
    would be 48. Either way, each key is still one allocation.
  - Reaching 1.5× needs one of two things: a lookup key that is not allocated
    at all, or a cheaper allocator (wave 4). The first would be a
    compiler-proven borrowed slice for `d.get(s[i:j])`/`d[s[i:j]]`, materialized
    only on insert.
- **Peak memory** is set by the collector's trigger, which lets garbage reach 3×
  the live set plus 4 MiB, applied to a live set of per-piece objects. Items 6.6
  and 6.10 own that.

**Where the `knucleotide` cost comes from: the accessor's test.** A
counterfactual compiler was built from this branch with two changes:
`myl_native_text_storage` reduced to `text + 1`, and sharing switched off.
Everything else was identical. In the same batch
(`str-views-accessor-counterfactual.json`), before the two fixes below:

- `this / before` was 1.057 [1.034, 1.086];
- `cf / before` was 1.018 [0.985, 1.046].

Every octet read now tests the view bit, and `knucleotide` reads a key's octets
several times per iteration: the hash, the probe comparison and the
get-then-set record check. Two changes recovered about half of the gap.
Afterwards `this / cf` was 1.013 [0.968, 1.032]
(`str-views-accessor-counterfactual-2.json`):

- The dictionary stores view keys as owned copies (§2), so only the queried text
  resolves its octets, once per lookup.
- The slice path tests the 9-octet minimum before it reads the receiver's
  header, so a short slice pays one compare.

What remains is the view test in `myl_native_text_hash` and in the queried key's
accessor. It costs about 2–3% on this dictionary-bound loop and is within noise
elsewhere. Removing it entirely would mean giving every text a payload pointer,
which grows every owned text by 8 bytes.

**Schematic and parser: unchanged.** Both read bytes, not `str` slices.

- The schematic ran 21 rounds × 3 inputs, with every SVG hash checked
  (`str-views-schematic.json`).
- The parser ran 11 rounds (`str-views-parser.json`).

## 5. Tests

- **Guest tests.** `tests/lang/text_views.my` has 8 tests. They run under
  `--gc-stress`, which collects at every allocation. They cover:
  - pieces outliving every other reference to their receiver: a slice and
    `split` lines returned out of the function that built the text;
  - views of views, four levels deep;
  - non-ASCII receivers: scalar indexing, `find`, `count`, `ord`, and `split` on
    a view that starts mid-text;
  - views as dictionary keys, interchangeable with owned text: lookup, `in`,
    `pop`, sorted keys;
  - the retention bound;
  - the policy edges: 8 and 9 octets, a quarter, whole, empty, clamped;
  - every consumer: `int`, `float`, f-strings, `str()`, `encode`, `join`,
    `upper`, `zfill`, `replace`, `isdigit`, `startswith`/`endswith`, `sorted`;
  - arenas: views of arena and outer text, `escape` of a list of views, and a
    view of a view escaping.

  The tests check answers, not representation, so they also pass on the base
  compiler. The exception is the retention test, which fails under an
  always-share rule.
- **Zig test** (`src/arena_managed_test.zig`, `TEXT-VIEW-2`). Four pieces of an
  outer text are made inside an arena and stored outward by a helper: a long
  slice, the whole text, `strip()` and a short `split` piece. Each traps
  `R_ARENA_ESCAPE`, as the copies did. `escape` of the same pieces returns their
  lengths.
- **C tests under UBSan and ASan+UBSan.** `tests/native_text_views_test.c` is a
  new suite in `scripts/test_native_memory.py`, run with the stress collector
  on. It covers:
  - which pieces become views;
  - the owner and offset of a view of a view;
  - the whole-receiver identity;
  - the owner surviving a flood of same-class allocations with only the view
    rooted;
  - a non-ASCII view's scalar count and code points;
  - a view's hash equalling an owned text's, and never being written into its
    offset word;
  - a dictionary storing a view key as an owned copy in its own region;
  - an arena view keeping an otherwise unreferenced outer owner alive through
    the arena scan;
  - a whole outer text sliced inside an arena becoming an arena object;
  - escape of an arena view of an arena text as an owned copy;
  - `split`'s long and short pieces.

  All nine existing suites also pass under both sanitizers.
- **Docs.** `docs/text.md` gains *Slices share their receiver's octets*, with a
  runnable front-slicing example. `SPEC.md` gains `TEXT-VIEW-1..4`, and
  `QBE-TEXT-BLOCK-1` now says that an *owned* text's payload is the header's
  tail.
- **Full guest suite.** All 337 guest tests in `tests/lang` pass under
  `--gc-stress` with this branch's compiler.

## 7. A build-cache hazard found on the way

The first measurements of this lane were wrong, and the cause is worth knowing.

1. `build_qbe_assets.zig` computes `content_hash`, the runtime tree's identity,
   in the build's configure phase.
2. I built the base tree (for the before arm) and this worktree with **one**
   `ZIG_LOCAL_CACHE_DIR`.
3. The second tree's configure was a cache hit on the first's. So this branch's
   compilers embedded the *base* runtime's `content_hash`, while `@embedFile`
   bundled the new sources.
4. The hash stayed stuck through later edits, because the cached configure had
   recorded the other tree's files as its dependencies.
5. `materialize()` reuses any existing `runtime/<content_hash>` directory. So a
   build from this branch that used a cache directory the base compiler had
   filled, or the default shared `~/.cache/mylang/runtime`, linked the **base**
   runtime.

One of this lane's benchmark batches silently measured a stale runtime before I
caught this. The check is to grep the installed compiler for the hash and
compare the `runtime/<hash>` directory's sources. Fresh private caches per tree
fix it. All numbers above come from verified runtimes.

Any lane that built a base tree and its own tree with one Zig cache, or that
times with the shared default runtime cache, should check its compiler's
embedded `content_hash` against its sources.

## 8. What is left

- **Allocation-free lookup keys** for `knucleotide`. A slice used only as a
  dictionary key operand could be a stack view, materialized only on insert.
  That is a compiler escape analysis plus a dictionary entry point, not a
  runtime representation change.
- **The per-object cost** that dominates `text_ops` and `scan_split` belongs to
  the allocation fast path and the collector's steady state (wave 4).
- **The accessor's remaining 2–3%** on text-keyed dictionary loops. It can be
  removed only by a payload pointer in every text, which costs 8 bytes per text.
- **A `bytes` view decoded to `str`** still copies.
