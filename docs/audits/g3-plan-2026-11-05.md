# G3: porting netlisp to Selka, section by section (plan, 5 November 2026)

Phase 4 of the EDA port closed on 5 November (`eda-port-roadmap-2026-10-22.md` §5.2), so G3, the full port, may
start. This plan covers G3 only. It replaces the one-line G3 row of the roadmap's §4.G with sections, gates and a
review stop after each section.

Two decisions from the user (5 November) shape it:
- **Scope: everything except the autorouter.** The user is writing a new router that reads the exported design file
  and does its work in Python. The export it reads stays in scope.
- **Process: one section at a time, with a review after each.** The language has not carried a project this large.
  Each section ends with a review of what the porting agents ran into. The compiler, language and standard-library
  fixes it calls for land on `main`, the ported code moves onto the fixed compiler, and only then does the next
  section start. No section starts while a review is open.

Sources: three surveys of 5 November (netlisp's structure, its tests and corpora, and G2's lessons), the roadmap, and
the phase 4 evidence. Every number below is from those surveys, except the per-section sizes, which are estimates that
step S0.4 replaces with measured import closures.

## 2. What G2 taught

G2 moved 99k Zig lines (74k product, 25k test) to 106k Selka lines with 1,250 tests and 34/34 goldens. It ran for
about 12 to 16 hours of wall-clock time with up to three lanes, against a 60-hour estimate. Measured from commits:
- G2a, the layout and skeleton: 0.9 h.
- G2b-d, three body lanes in parallel: 4.5 h.
- The ownership migration of 25 October: up to 3.7 h.
- G2e, integration: 1.3 h.
- G2p, speed: 5.5 h, which took it from 1.95x to 1.05x Zig's wall time.

What worked and carries over:
- **One Selka module per Zig file**, with shared types moved to leaf modules and re-exported. A cycle is broken with
  a record of function fields (`eval_hooks.Hooks[S]`) set once at start-up. Every moved declaration is recorded in a
  `[moves]` map.
- **Skeleton first.** A generator writes every body as a typed hole; `check` then reports only `E_TYPED_HOLE`.
- **Lanes own disjoint files** and work in dependency order. An edit outside a lane's files is a `shared:` commit or
  a request to the file's owner.
- **Zig emulation is checked against captured Zig output:**
  - the hash map, slot for slot (`support_zig_hashmap`, 41 scenarios);
  - the sort's tie order (`support_pdq`, 98 scenarios);
  - the math functions (`support_math`, 4,678 values).
- **Goldens are compared on a merge preview before any merge** (`git merge-tree` of the lane heads). Every merge then
  runs all tests and goldens.
- **Differential tests against the real Zig functions** (power budget, check grammar, BOM resolve). They found bugs
  the ported tests missed.
- **Nine idioms from G2p, applied from the start:**
  1. accessors return `from` borrows;
  2. bind `const`, not `mut … = copy(…)`;
  3. scanners keep their cursor in locals;
  4. move with `take`, `exchange` and `own` instead of copying and resetting;
  5. write through `mut` element places;
  6. use lend-style map lookups;
  7. pass read-only inputs as parameters, not inside records;
  8. append operands one at a time;
  9. build lookup indexes once.

What cost time, and what this plan changes because of it:

| G2 cost | Change in G3 |
| --- | --- |
| The skeleton emitted public functions only, so about 250 private functions were missing rather than holes. Lane 1 became the long pole | The generator emits every function, private included (S0.3) |
| Holes hid ownership errors | Fixed on `main` (d1e262f48); lanes still build `main.my`, not only `check` |
| `check ENTRY` skips modules the entry does not import, and `check` accepts shapes `build` refuses | Fix before S1 (D-G3-4); until then lanes build the whole program |
| A function cannot return a record that holds a capability, so 76 test files copy a 1.5 KB evaluator literal | Fix before S1 (D-G3-4) |
| The porting guide in the tree was written for an older compiler; the promised idiom guide was never written | S0.2 writes it before any lane starts |
| `mylang fix` looped on a compiler bug during the 25 October migration | Fixed on `main`; every migration is tested on the port before it lands (§3.6) |
| Every golden mismatch was a port bug: Zig `\\` literals with no trailing newline, a constant 10 for 15, an inverted test | The guide lists these; the multiline-literal audit script runs in every lane |

Still open on `main` from G2's lists, to be confirmed in S0:
- Records cannot hold borrows (C5; the roadmap does not plan it).
- `take` and `exchange` refuse record-typed places and list elements.
- A `mut` parameter's record field cannot be moved on.
- A `from` accessor cannot return an empty list.
- `lists.extend` copies its elements.
- `math` lacks `log10`, `exp`, `atan2` and a float `pow`.
- No `chmod` or `realpath`. (S0 corrected two items this list had: `hashes.sha256` and `filesystem.stat` exist.)
- Several items G2 left as unknown: moving `match` payloads, `unwrap_or` on a borrowed option, integer `/`, sin and
  cos one ulp off in about 2% of arguments.

The edit loop is ready for the size. On 5 November, at 400k lines: `check` after an edit 1.75 s at most, a debug build
after an edit 4.04 s at most, one module's tests 1.31 s, and a cold release build 250 s in 6.0 GB.

## 3. Ground rules for every section

1. **One repository.** A new repository, `~/ai/canopy/netlisp-selka` (D5, accepted 22 October), whose layout mirrors
   netlisp's: `src/placement/drc.my` for `src/placement/drc.zig`. It starts from G2's port, copied with a provenance
   note (eda-bench `g2p/integration` b314cc2), with its harness, support modules and maps. eda-bench stays as it is.
2. **One netlisp base.** Every section ports netlisp at one pinned commit. The design corpus is pinned the way
   stage 2's `inputs.tsv` pins it: the `projects/designs` repository at a commit, plus the saved layouts a section
   needs, which are large local files. Which base, and when the port catches up with netlisp, is decision D-G3-2.
3. **One pinned compiler per section.** The compiler changes only at a review stop, where the port moves to the fixed
   compiler with `mylang fix` (roadmap §4.H, R-6).
4. **The oracle is netlisp itself.**
   - **Tests:** netlisp's own tests port with the code, matched by name with `check_tests.py`. Every section reports
     the matched count and lists the unmatched.
   - **Outputs:** the Selka binary and netlisp at the base run the same command lines on the corpus. Their outputs
     must be byte-identical after a normalisation that drops only `#` header lines, timestamps and build identities.
     `scripts/corpus_diff.sh` in netlisp already diffs two binaries this way. The harness gains per-case commands,
     stdout capture and the normalisation (S0.1).
   - **Differential tests** against the real Zig functions, where the ported tests are thin (G2's practice).
5. **The friction log is the review's input.**
   - Every place where the language, the compiler or the standard library forced a workaround, a copy, a slow form or
     a long hunt gets an entry: an id (`F-S1-12`), a minimal repro, the sites it affects and the time it cost.
   - A workaround is allowed during a section, so the section can finish. It must be logged and marked in the code
     (`# friction: F-S1-12`), so it can be removed once the fix lands.
   - A hidden workaround is a defect in the lane's work.
6. **The review stop.** When a section's gates pass, the coordinator writes a review packet:
   - the section's gate table;
   - its time against the estimate;
   - the friction log grouped by cause, with counts;
   - the build telemetry summary (§3.9);
   - the fixes proposed, ranked by sites affected and by cost.

   The user and the coordinator choose what to fix. Compiler lanes land those fixes on `main`, each breaking one with
   its `mylang fix` migration, tested on the port before it lands. The port then moves to the new compiler, its marked
   workarounds come out, and the section's gates run again. Then the next section starts.
7. **At most three lanes at once** (the user's rule of 2 November), the coordinator's review lanes included.
8. **Evidence stays out of git**, as in the mylang repository: logs, captures and binaries go to
   `~/ai/canopy/mylang-evidence-archive/experiments/g3/<section>/`.
9. **Every compiler invocation is recorded** (the user, 5 November: to see how well the compiler and its caches work on
   a large real project).
   - Lanes run `mylang` only through the repository's wrapper, `tools/my`. It adds the compiler's own reporting flags:
     `--report` on `build` and `run`, and `--json` and `--engine-report` on `test`.
   - The wrapper appends one record per invocation to
     `~/ai/canopy/mylang-evidence-archive/experiments/g3/telemetry/<lane>.jsonl`. Each record holds the command, the
     exit status, wall and CPU time, peak RSS, the compiler's identity, the commit and dirty-file count, the load, and
     the parsed cache report or test counters.
   - `tools/telemetry_report.py` summarises a section's records:
     - edit builds, cold builds, checks and test runs, with the median and p90 of each;
     - unit reuse and program replay rates;
     - test reuse rates;
     - the slowest invocations;
     - every place a cache should have served and did not.
   - **Cache disk space** is sampled too (the user, 5 November: Zig's caches used to grow without bound, and that
     should be fixed). Every store is sampled at most every 15 minutes, in the background, and at each section's start
     and end:
     - the port's `.mylang-cache` and its tiers;
     - the per-user mylang stores (the object store, stage artifacts, native tests, compiler artifacts, verification
       evidence);
     - any `.zig-cache` in the port;
     - the Zig global cache;
     - leftover build staging directories;
     - the netlisp oracle builds' caches.

     The summary shows each store's size over the section, the bytes added per build, and whether retention held it
     under its cap. A store that grows without bound, or past its cap, is a finding.
   - That summary is part of each review packet (§3.6). A cache that misses where it should hit is a compiler finding
     like any other.

### 4.1 Gates every section passes

1. Every ported test passes, in debug with the leak check, and the name-matching report lists no unexplained gap.
2. Outputs are byte-identical to netlisp at the base for every command the section delivers, on the pinned corpus.
3. **Speed:** the release build is within 1.25x of netlisp's LLVM ReleaseFast wall time on the section's commands,
   by geomean, and any command above 1.5x gets a profile. netlisp's shipped build uses Zig's own back end unless
   `-Dllvm` is set; the comparison uses LLVM, as phase 4 did. Instructions are tracked, not gated (as for R-2).
4. **The edit loop on the whole port as it stands:** `check` after a one-line edit within 2 s, a debug build within
   5 s (R-5).
5. **Copies:** no `copy(...)` on a per-element or per-iteration path without a friction entry (R-1).
6. The friction log and the review packet are written.

### 4.2 Inside a section

1. **The cut.** A script computes the section's file set from its command roots: the import closure, with stubs at
   the boundary. The coordinator approves the cut and the module layout before any body is written, as in G2a.
2. **The skeleton.** Generator v2 writes every function, private ones included, as a typed hole, and every test as a
   stub that names its Zig test. The whole program builds with only `E_TYPED_HOLE`.
3. **Lanes.** Up to three, each owning disjoint files, in dependency order. Lanes build `src/main.my`, not only
   `check`, and run the section's goldens on a merge preview before asking to merge.
4. **Integration.** At each merge the coordinator runs all tests, all goldens and the edit-loop check.
5. **Speed.** One pass against netlisp at the end of the section. It fixes port-side waste only; compiler-side causes
   go to the friction log.
6. **The review stop** (§3.6).

## 8. Decisions for the user

**Accepted 5 November (user): all five, as recommended.** D-G3-2's question, whether the port is to replace
netlisp or to prove the language, stays open until the catch-up decision after S5.

1. **D-G3-1, the router cut.**
   - Cut (c): the router, its siblings and the route drivers in the server and the CLI.
   - The placement optimizer's routed finishing passes come out too.
   - The oracle for placement results is netlisp at the base with a small patch that skips those passes, maintained
     beside the harness as the stage-2 dumper patch was.

   **Recommended: as stated.** The alternative, cut (a), keeps 64k more lines of routing code that the new router
   replaces.
2. **D-G3-2, the netlisp base and catching up.**
   - (a) Freeze `5c135b37` for all of G3. S1 brings stage 2 up to it, which also measures what a catch-up costs. After
     S5, a last section catches up with netlisp's HEAD if the port is to replace it.
   - (b) Move to netlisp's HEAD at the start of each section, and catch the ported sections up at each review stop.

   **Recommended: (a).** netlisp changes by about 126 commits a fortnight. Under (b) every review stop would also carry
   a catch-up of everything ported so far, and that cost grows with the port. This choice depends on a question only
   the user can answer: is the Selka port meant to replace netlisp, or to prove the language at this scale?
3. **D-G3-3, who implements.** The current mode: the coordinator (Claude) with Sonnet lanes, at most three at once, as
   in G2 (12–16 h against 60 h). The alternative is Codex runs, with Claude reviewing. **Recommended: the current
   mode,** revisited at the S1 review.
4. **D-G3-4, which known compiler items land before S1.**
   - `check` skips modules the entry does not import, and `check` accepts shapes `build` refuses.
   - A function cannot return a record that holds a capability.
   - `math.log10`, `exp`, `atan2` and a float `pow`.

   **Recommended: fix these three before S1**, one compiler lane, about 4–8 h, and leave every other open item to
   the reviews. The alternative lets S1 rediscover them, which costs the first section time on known problems.
5. **D-G3-5, self-hosting (H1).** The roadmap runs it beside G3, but at most three lanes run at once.
   **Recommended: H1 waits until G3 finishes**, unless a review stop shows idle lanes. G3 is the user's goal; H1 is
   not on its path.

## 9. Tracking

The roadmap doc ("EDA port roadmap") gets a G3 row per section: S0, S1, S2, S3a, S3b, S4, S5 and the catch-up. Each
row has its estimate, start, finish, elapsed time and status, and each review stop has a gate row. The 1.5x review rule
of the roadmap's §5.1 applies to each section. The roadmap's §4.G G3 row points to this plan.
