## 1. Summary

The guest-side loop is already fast: a body edit checks in about 80 ms and runs two tests in under half a second (log, 40-edit cohort, 12 Oct). The compiler-side loop is not: a one-line edit anywhere under `src/` recompiles the compiler in 2 to 7 seconds and then invalidates every test verdict for that tree, so the gate that must pass before finishing costs 10 to 17 minutes and holds the one gate slot. An unchanged full verification still takes 34 to 37 seconds. Nothing that costs minutes is shared between agents: verdicts, receipts and stage caches are keyed to the worktree path, to the full environment (including the agent's `CODEX_THREAD_ID`) and to a hash of every production source, so ten agents on the same base commit run ten identical cold gates through a single FIFO slot.

Three structural facts explain most of the loss:

1. **One monolithic compiler identity is in every key.** `build_identity.zig` digests all of `src/`; that digest is bound into guest test receipts, the shared program cache, the stage caches and, via the `mylang` binary as a declared input, every cached `zig build` test step. "What ran" is never the key, only "what compiled it".
2. **Identities embed the agent and the tree, not the work.** The verdict cache hashes the entire live environment (`build.zig:117-133`); the coordinator keeps almost all of it too (`scripts/verify_cache.py:320-360`); receipts and test binaries embed absolute worktree paths; the per-worktree `TMPDIR` and `ZIG_LOCAL_CACHE_DIR` exported by `dev-env.sh` make every worktree's environment digest unique by construction. Even Zig's own build cache is per tree only because the project feeds it absolute paths. Sharing tiers exist but are opt-in and unused on this machine.
3. **Tests pay for the compiler as a process.** Most Zig unit and core tests build and run guest programs by spawning the 239 MB Debug `mylang` (often with a private temporary cache), and 1,790 guest tests refuse receipts by policy. The gate is therefore dominated by process churn that no cache is allowed to absorb.

Around these sit an admission scheduler that serializes everything through one gate slot and drains the machine for timing windows, an object store with 1.87 million files in one flat directory and no working eviction, 451 worktrees, 135 GB of per-lane caches, a laptop CPU in `powersave` at 79 °C, and 13 GB of stale scratch pinned in tmpfs with swap full.

The architectural move is to make the cache **output-keyed, path-free and machine-wide**: component identities instead of one compiler hash, verdicts keyed on the program that ran, an allowlisted environment, a single sharded content-addressed store with its own garbage collection, and one machine-level scheduler that deduplicates identical work across agents. Section 5 lays this out; Section 6 ranks the changes with expected gains. Several quick wins need no architecture at all (Section 7).

## 3. Where the time goes

### B1. The compiler identity is in every key, so every `src/` edit is a cold gate

- `build_identity.zig:1-30` digests every production source under `src/` plus the Zig version and optimize mode.
- Guest test receipts bind it (`src/core/test_runner_receipt.zig:56,98`), as does the shared program key (`src/core/driver.zig:286-295`) and every stage-cache key (`src/core/stage_store.zig:34-57`: lowering, optimizer, emission and native receipts).
- In `build.zig`, every cached test step declares the `mylang` binary as an input (`tool_inputs`, build.zig:153,568), and the test binaries embed the absolute `core_path` and fixture paths (build.zig:403,409), so all test executables change too.
- Result: after any compiler edit the coordinator reruns core, unit, cli, golden, idioms, incremental, interfaces, parser hints, doc coverage, doctest, formatting, lint and component groups. Plain `zig build test` is worse: `tool_inputs` makes even pure-Python groups rerun (verification_cache 44 + 26 + 11 s, fuzz, juice_cache), and the core shards are declared with side effects so all eight rerun every time.
- Nineteen docs are embedded into the compiler (`src/user_docs.zig:20-38`), so editing `docs/primer.md` changes the compiler bytes and triggers the same near-full gate.
- The project named this on 5 October ("DL-2: key guest results by what they run, not by the compiler"), but what shipped keys receipts by Core IR **and** the compiler identity, and the latter does the invalidating.

### B2. Nothing minutes-long is shared between agents or worktrees

- `build.zig:117-133` hashes the complete sorted environment into every verdict (`env -0 | sort | sha256sum`). `dev-env.sh` exports `TMPDIR=$root/.tmp/work` and `ZIG_LOCAL_CACHE_DIR=$root/.zig-cache`, so two worktrees can never share a verdict even with identical sources and tools.
- The coordinator's `normalized_environment` (`scripts/verify_cache.py:320-360`) strips only `_`, the telemetry directories, admission markers, `GIT_*`, `BASH_ENV` and function exports. Wave 2 recorded a launcher that differed solely in `CODEX_THREAD_ID` and missed all 46 groups. `common` also carries `"root": str(root)` (verify_cache.py:897).
- Store placement: `units-v1`, `core_rt`, `core_number_text` and the tool memo are the only per-user stores. `programs-v1` (whose key contains no paths) and the stage packs sit per worktree purely by location; receipts and manifests embed absolute entry paths (`test_runner_receipt.zig:99-100,530-538`); the replay key includes the cwd realpath and the entire environment minus three variables (`src/core/build_replay.zig:109-155`).
- The shared tiers (`MYLANG_COMPILER_SHARED_CACHE`, `MYLANG_TEST_SHARED_CACHE`, `--shared-cache-dir`) are opt-in, unset in `dev-env.sh`, their documented directories do not exist on this machine, and the test tier covers only zero-argument `bool` tests. A `DeterminismMismatch` in the shared tier fails the build instead of missing (`driver.zig:280-283`), one reason it is not the default.
- Zig's own cache is per tree for the same reason, not because of Zig: compile manifests record build-root sources as cwd-relative paths plus content digests, and the configure-cache key excludes the build root. What pins them to a tree is the project's configure-time strings: `build_identity.zig:40,54-58` passes the realpath of the build root, `build.zig:407-410` bakes fixture and lang-test realpaths into test options, and Run steps hash resolved absolute directory arguments. So `identity.zig`, `mylang`, `units`, `core`, `cli` and `golden` are per tree today; only `selka-components`, the small objects and the small test roots would already share.
- Consequence at the current scale: a ten-session wave on one base commit runs ten cold gates of 600 to 1000 s each, serialized through the single gate slot: roughly 100 to 170 minutes of pure queue for identical work. The queue statistics in Section 2 are the result.

### B3. The gate's work is process churn the cache cannot absorb

- 911 of 1,564 tests in `src/root_test.zig` live in the 90 files that use `native_execute`; 620 of 1,016 core tests are in files that spawn the compiler or `zig cc`. 43 core test files pass a per-test temporary `--cache-dir`, so nothing is reused between tests. Every run is a fresh `mylang run` process of a 239 MB Debug binary, even a re-run of an already built program with a different `--max-steps` (`src/native_execute.zig:394-412`).
- Budget sweeps (`.again()` loops, 46 sites in 5 files) dominate the slowest shards: `nominal_providers` does 1 build and 109 runs in 53.6 s; `resource_source` 33 s; `resource_io` 27 s. Direct execution of the built binary with runtime limits would be milliseconds per run.
- Shard balance is positional (`index % N`), so the unit root's slowest shard takes 153 s while the others take 17 to 60 s; the critical path is the slowest shard.
- Declared `max_rss` (2.5 GiB per unit shard, 1 GiB per core shard) is 10 to 30 times the observed 67 to 578 MB, so the build runner throttles concurrency: about 1,390 summed step-seconds over 621 s elapsed is 2.2 steps running at a time on 20 threads.
- The 1,790 `--release --verify-facts` and leak-check guest tests never read receipts (`test_runner_receipt.zig:366-400`); they are the 13 s critical path of every warm gate, by policy (closeout S06).
- Three test shards from a deleted worktree have been hung since 21 September, blocked in `accept()` on a socket whose client died (`[mylang] <defunct>`), with 21 zombies behind them. There is no timeout on that path. DL2's cancellation work addresses the class; the processes are still there.

### B4. The warm floor is policy plus unattributed overhead

Warm complete verification is 34 to 37 s, of which 23 to 28 s is gate occupancy. Inside it: language fact/leak 13 s (critical path), juice collectors 4 to 5 s, spec-history 2 s, Guardian about 1 s twice, component preparation and input discovery about 1 s each. 15 to 20 s of the window is attributed to nothing in the telemetry; candidates are `zig build` configuring a 135-step graph, the admission settle timer, and the admitted child re-importing and authenticating its own code. Outside admission the Python coordinator spends 3 to 6 s in a retained session and 8.5 to 11 s one-shot, including `tool_contract` twice (about 170 `ldd` subprocesses) and 154k to 594k stat calls for snapshot validation. Every warm verification still takes the single gate slot. The persistent-verification-server plan explicitly keeps all of this ("persistence alone cannot remove most complete-verification time"); it would save the 3 to 10 s of preparation.

### B5. Admission is a single FIFO queue that drains the machine for timing

- `scripts/build-slot.sh`: 3 build slots and 1 gate slot machine-wide (`dev-env.sh` sets 2 gate slots and 8 G build memory for agents that source it); memory is checked once at admission, nothing is reserved; a 5 s global settle after every admission caps the whole machine at about 12 admissions per minute; a queued timing request stops all admissions and drains running jobs.
- Head-of-line blocking: a 35 s warm verification queues behind 600 to 1000 s cold gates; wait reasons in the logs are "earlier tickets must run first" 553 times, "gate slot busy" 286, "settle delay" 198, low memory 25.
- Two admission domains exist on the machine: `dev-env.sh` points at `~/.cache/mylang/slots`, where the live locks and queue tickets are; `build-slot.sh` without that environment uses `/run/user/1000/mylang-slots`. CLAUDE.md never mentions `dev-env.sh`, so an agent following CLAUDE.md alone is admitted independently of the codex agents. Right now the default directory is idle and the dev-env one has a timing holder and two gate waiters.
- `scripts/verification/scheduler.py` already implements a SQLite scheduler with CPU and memory accounting, priorities, job-key dedupe with subscribers and leases. Nothing uses it.

### B6. Stores grow without bound and the hygiene jobs do not run

- `~/.cache/mylang/core-runtime/units-v1`: 1,873,045 entries in one flat directory (936k objects plus a `.sum` each; median object 3.3 KB), 27 GB; the directory inode alone is 220 MB; about 200k new entries per day since 7 October; 134,451 stale claim lock files under `work/`. The store cap is 10 GiB (`prune-caches.sh:66`).
- Eviction cannot run: every build holds a shared lease on `.retention.lock` for the whole link, the pruner needs it exclusively and skips with "busy"; the pruner does `find` + `sort` + `du -sx` over the whole store each run; the "hourly" prune in CLAUDE.md:180 is not installed anywhere (no crontab, no user or system timer); and the pruner does not see the out-of-tree `zig-local-cache-<lane>` directories where Zig caches actually live now.
- Zig caches: a representative lane cache is 6.8 GB and 3,799 files, of which 20 `mylang` binaries are 4.7 GB and 22 test binaries 2.9 GB; each `src` edit adds about 0.7 GB and Zig never evicts. `zig-out` is 964 MB because `build_verification.zig:247-249` copies the compiler and the test binaries a second time. 49 installed Debug compilers at 239 MB each sit across worktrees.
- Unbounded and uncollected: the stage packs (`stages-packed-v1`, in no prune rule), 567 `core_rt` variants plus 284 runtime `.c` copies, 975 tool-identity files.
- Cache sprawl: `~/.cache/mylang` holds 749 lane directories, 3.8 million files, 135 GB (14 `zig-local-cache-*` dirs alone are 24 GB); `.selka-agent-cache` is 50 GB; 451 registered worktrees (279 with HEAD older than 7 days), 646 branches, a 3.2 GB `.git`. The `/home/epentland/ai` SSD is at 91 % with 166 GB free.

### B7. Per-build fixed costs and key design in the guest pipeline

- Unit object keys include the digest of the whole runtime C source (`src/core/unit_cache.zig:43-56`), although `zig cc -c x.ll` reads no runtime input (`driver.zig:699-707`). Any runtime `.c` edit recompiles every unit at about 1 CPU-second each (195 s for 760 units at 4 lanes).
- Replay re-reads and BLAKE3-hashes every source in full with no stat shortcut and copies the executable rather than linking it (`build_replay.zig:50-75`, `unit_cache.zig:384-395`). The toolchain identity is validated 5 to 6 times per build.
- Validating cache hits now costs more than compiling on a large edit: at 191k lines, optimizer 1.3 s with all hits and emission 1.6 s with 759 of 760 units reused, about 2 ms per hit, against 0.38 s of native work. Each process also rescans every stage-pack index at first lookup (`stage_pack.zig:112-130`).
- Lowering and optimizer keys include a catalog digest over all records and every function's ordinal id, name and signature (`lowering_cache.zig:98-110,253-271`, `ir_snapshot.zig:109-139`), so an interface edit, an added function or a new generic instance re-lowers and re-optimizes the whole program and re-renders every unit. Objects survive because they are keyed by text.
- Unit misses hold exclusive per-key claims until the whole batch publishes (`driver.zig:629-672`), so an agent that needs one overlapping key waits for another agent's entire batch; lanes default to the CPU count per agent, so twenty agents oversubscribe 20 threads by design.
- Optimized Debug (`-O2` per unit) became the default on 10 October. At 48k lines, `-O0` compiled in 3.3 s against 50 s at `-O3`; cold native at 191k is 219 s. The edit loop pays this on every large-unit edit and every cold build.

### B8. Inner-loop friction in the install graph

- Guardian gates every install (`build.zig:638`, `maybeGateInstall` in guardian-zig). It runs in parallel with the compile, so the added latency is about 1 s on a no-op build, but while it has findings the binary is not installed and `zig-out/bin/mylang` silently stays stale. `stage.sh`, the documented workaround, is unsound: it hard-codes `.zig-cache/o` (wrong whenever `ZIG_LOCAL_CACHE_DIR` is set, as the docs recommend), picks the newest binary by mtime across branches and optimize modes, and still references the retired `mylang-io`. `zig build affected-compiler` (`build.zig:579-582`) already installs an ungated copy correctly.
- `component_build` runs on every build as a side-effect step (0.4 to 0.6 s) instead of being cached on its declared inputs.
- `zig build --watch -fincremental` was measured on 5 October at 0.9, 13 and 17 s per edit against 20 to 31 s then; nothing uses it, and a September note says plain `-fincremental` without `--watch` gave no gain.

### B9. The machine itself

- CPU governor `powersave`, energy preference `balance_performance`, 2.6 GHz at 79 °C under a load average of 3. For a build box this is a direct throughput loss and a thermal-throttling risk.
- `/tmp` is a 24 GB tmpfs holding 13 GB, of which about 7 GB are `frontend-*` experiment directories from 8 October, a 1.4 GB tar and a 1.7 GB debug-runtime directory. `Shmem` is 6.5 GB and the 8 GB swap is 100 % full with those pages. Memory pressure is currently low (PSI avg300 0.27 %), but gate concurrency is already memory-throttled (B3) and the admission wrapper trusts `MemAvailable`.
- `earlyoom` prefers to kill `mylang`, `zig`, `cc1` and `python3`, so an overcommit shows up as a failed test rather than a slow one.

## 4. What the prior plans already cover, and what they miss

Done and merged: receipts keyed by Core IR plus compiler identity; per-unit objects keyed by LLVM text in a per-user store; verdict caching in `build.zig` with declared inputs; shared compiler-artifact and test-receipt tiers (opt-in, narrow); FIFO admission with memory thresholds and exclusive timing windows; the `tooling_unit` and `text_scalar_unit` root splits; the retained verification session with an inotify watcher; declarative input projection; the 12 October telemetry fix.

Planned: a three-worker persistent verification broker (plan only, not started), DL4 producer identities for independently built components, DL2 calibrated deadlines, further root splits, the complete ordinary-edit matrix, self-hosting with a 1.5x-of-Zig acceptance bound.

Rejected or stalled: cross-snapshot stat memoization and guest discovery indexing (rejected in the closeout), `zig build --watch -fincremental` (no follow-up), function-level Zig test reuse (explicitly not promised), the lane-B velocity harness (never built; `velocity/backlog.json` still refers to QBE).

Not addressed anywhere: path- and environment-independent identities; sharing verdicts between agents by default; keying on what ran rather than on the compiler; receipts for fact/leak modes; a machine-wide store with working eviction; a scheduler that deduplicates identical gates; the Python coordinator's fixed cost; swap, tmpfs, governor and worktree count. CLAUDE.md still says an unchanged `zig build test` "takes seconds" (it is 34 to 37 s through the coordinator and reruns all core shards when run plainly), that the prune runs hourly (it does not run), and that Zig's configure cache forces per-worktree caches (the project's own absolute strings do).

## 5. Target architecture: one cache, many agents

The principle: **a cache entry is identified by the content that produced it and the content it produces, never by who or where.** Five layers.

**L1. Identity model.** Replace the single `compiler_identity` with component identities derived from each module's import closure (the walk `build_identity.zig` already does): front end, lowering, optimizer, emitter, runtime, test runner and driver. Each stage key binds its own component plus the digests of its upstream artifacts. Verdicts get an *early cutoff*: on a miss of the IR-based key, build the program and look the verdict up by (program object digests + runtime objects + runner protocol + execution settings). A compiler edit that does not change what a test runs then reuses the verdict, which is the common case for front-end, diagnostic, tooling and docs edits. Fact and leak modes become part of the key instead of a refusal. Environment goes through an allowlist (`PATH` contents by digest, `HOME`, locale, `MYLANG_*`, `SELKA_*`, `ZIG*`, toolchain variables), and every absolute path in a key, in a test binary or in a Zig configure-time argument becomes a path relative to the root passed at run time.

**L2. One machine-wide content-addressed store.** A single per-machine store with two-level sharded directories, the `.sum` folded into an object header, an in-memory or SQLite index, an append-only access ledger for LRU, and mark-and-sweep eviction that tolerates concurrent readers by re-verifying on miss instead of taking a store-wide lease. It holds objects, runtime objects, linked programs (keys already path-free), stage artifacts (lowering, optimizer, emission, receipts), test receipts and gate verdicts, each under its own namespace. The per-worktree `.mylang-cache` shrinks to replay records and scratch. Claims are released per unit on publish, not per batch. Zig's local cache joins the same policy: one shared local cache for all worktrees, with the configure cache scoped per tree (`-Dtree=<realpath>` or `poisonCache`), relocatable identity and option inputs, and whole-generation rotation for eviction.

**L3. One machine-wide execution service.** A small daemon owning (a) a global job-token pool for `zig cc`, links and test processes so twenty agents share 20 threads instead of each assuming all of them, (b) event-driven admission with priorities (interactive, merge, qualification), fair share per agent and resource accounting, replacing the 5 s poll, the 5 s global settle and the single gate slot, (c) deduplication: identical action keys submitted by several agents run once and all subscribers receive the result (`scripts/verification/scheduler.py` already has the schema), and (d) a cpuset partition for timing runs (say 4 reserved cores) instead of draining the whole machine.

**L4. Verification as a per-commit job with shared receipts.** Integration runs one complete gate per integrated commit and publishes receipts to L2. An agent's pre-finish verification runs only the actions whose inputs differ from the nearest verified ancestor: its own diff. With L1 that is the Zig roots whose component identity changed plus the guest tests whose program changed. Always-fresh groups shrink to genuinely host-dependent collectors, which move to a qualification profile.

**L5. Resident sessions for the inner loop.** For guest projects, a per-worktree compiler session that keeps the project index, typed program, Core IR and pack index warm (the existing `check-session` extended to build, run and test), with `-O0` units in the edit loop and `-O2` promoted in the background. For compiler edits, `zig build --watch -fincremental` guarded by a clean build before any gate, runtime test filters instead of a binary per filter set, and Guardian moved off the install path into the gate.

Hygiene is part of the architecture: eviction and worktree garbage collection on timers, lane caches consolidated into L2, tmpfs scratch forbidden by `TMPDIR` policy, and the CPU governor set for a build box.
