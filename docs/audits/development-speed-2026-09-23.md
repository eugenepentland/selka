# Development-speed audit — 23 September 2026

**Question asked:** what would most increase development speed with mylang? The user
clarified the target mid-audit: *development speed on large codebases* — fixing bugs and
adding features in an existing project — where mylang should beat Rust, Zig and Go through
better tooling and faster compilation. Greenfield work against Python is a secondary
concern, since Python will always win there.

**What is new here.** Earlier audits scored scripted idiom probes (Lane C), latency ladders
on mylang alone (Lane B) and static counts. `velocity/goal.json`'s headline lane — A, task
velocity — still had `baseline: null`, and nothing had compared mylang against Rust, Zig and
Go at the same project size. This audit measures both:

1. a **scale ladder**: one generated project, identical in shape, in all four languages at
   10k, 50k and 200k mylang lines, timed through cold build, no-op build, and check, build
   and test after an edit;
2. **maintenance trials**: fresh agents fixing a planted bug and adding a feature to the
   4,200-line Lox interpreter that exists in all four languages with the same design,
   graded by hidden tests and the conformance corpus;
3. a **tooling probe** of mylang's large-codebase commands at 50k lines, green and red;
4. the **greenfield pilot** (mylang vs Python, five tasks, plus a primer experiment), kept
   because it is the only onboarding measurement.

Everything ran against a ReleaseFast build of `main` 35fcbc02 (compiler sha256
`b650c4bb…`, worktree `mylang-worktrees/devspeed-audit-20260923`). Agents were Claude
Sonnet 5 subagents with no prior mylang context, one run per cell. Timings are minima of 2–3
samples on the 20-thread i7-12700H: the ladder is pinned to the P-cores (CPUs 0–11) and
the concurrent maintenance agents' toolchains to the E-cores (12–19).

## Verdict

1. **At scale, the build path is where mylang loses, and it loses badly.** Checking stays
   close to the others. Building does not: after a one-line edit, a Debug build of the 50k
   project takes 6.9 s (Go 0.16 s, Rust 0.71 s, Zig 0.74 s), a no-op build 6.3 s, a cold
   build 510 s (Go 2.4 s, Rust 5.0 s, Zig 0.8 s). At 200k lines the build runs out of
   memory. A 50k no-op build spends 8.2 of its 9.5 s in the frontend, re-lowering the
   whole program that `check` has just verified in 0.77 s. The 17 September scorecard
   named this (§2.3, per-function fragment reuse); it never landed. Nothing else in this
   audit matters as much for large codebases.
2. **The default `build` is a release build.** `mylang build` means `--mode ReleaseFast`:
   LLVM `-O3` with LTO. Agents building the Lox port waited 17–39 s per build, and a
   comment-only edit costs 4 s of LTO relinking. Rust, Zig and Go all default to fast
   builds.
3. **Maintenance on a 4k-line codebase: mylang ties Zig and trails Go and Rust.** All
   eight maintenance runs passed. Adding `break` took mylang 21.1 min (Go 13.7, Rust 16.9,
   Zig 21.6); fixing a GC bug took 13.0 min (Go 8.2, Rust 8.9, Zig 13.0). Orientation
   before the first edit is similar across languages; mylang's extra time comes after it,
   from release builds and a test harness that cannot exercise capability-bearing code.
4. **The large-codebase tools exist but nobody uses them, and some are mis-shaped.** No
   maintenance agent in any language used anything but `grep` and file reads — including
   the mylang agents, whose `context`, `tests-for` and `index-project` were built for this.
   At 50k lines `index-project` emits 36 MB of JSON, `test --affected` is slower (8.0 s)
   than a plain cached test run (1.4 s), and `tests-for` fails while the project has a
   type error.
5. **Code outside the compiler repository breaks daily.** Eleven hours of `main` changed
   22% of the Lox port's non-blank lines, lost its 11 end-to-end tests, and the shipped
   migration script corrupted the project. Large codebases amplify this in proportion to
   their size.
6. **Greenfield (secondary): mylang agents are correct but 2.7× slower than Python
   agents,** almost all of it spent reading ~190 KB of documentation before the first edit.
   A one-page primer cut the reading by two thirds and context tokens by 17–52%, but not
   wall time.

Seven fixes for problems the trials exposed are committed on `fix/devspeed-audit-20260923`
([§10](#10-fixed-during-this-audit)). The ranked recommendations are in
[§9](#9-recommendations-ranked-for-large-codebases).

## 1. Scale ladder: mylang against Go, Rust and Zig

**Shape.** `M` modules in an import chain; each declares a record/struct and `F` functions;
function `i` of module `m` builds a list of `n` ints, folds it through the record and calls
function `i` of module `m−1`; each module has one test; `main` calls every function of the
last module. Generated by `gen_scale.py` with identical structure per language (mylang is
shorter per function: ~11 non-blank lines against 14–16).

| Tier | Modules × functions | mylang | Go | Rust | Zig |
| --- | --- | --- | --- | --- | --- |
| 10k | 25 × 36 | 10,116 | 13,869 | 13,865 | 15,594 |
| 50k | 120 × 38 | 51,043 | 70,006 | 70,002 | 78,766 |
| 200k | 480 × 38 | 204,043 | 279,886 | 279,882 | 314,926 |

**Commands.** mylang `check main.my`, `build main.my --project --mode Debug` (QBE; the
default release build is reported separately), `test main.my`; Go `vet ./...`,
`build ./cmd`, `test ./...`; Rust (one crate) `cargo check`, `cargo build`, `cargo test`;
Zig `build-exe -fno-emit-bin`, `build-exe -O Debug`, `zig test`. "Edit" changes a constant
in a function body in the middle module; "interface" appends a new public function there.

**Results** (seconds; mylang Debug / Go / Rust / Zig):

| Step | 10k | 50k | 200k |
| --- | --- | --- | --- |
| cold build | 35.0 / 0.73 / 1.32 / 0.50 | **509.6** / 2.37 / 4.97 / 0.79 | **out of memory** / 18.0 / 22.2 / 2.31 |
| no-op build | 1.00 / 0.03 / 0.02 / 0.47 | **6.28** / 0.03 / 0.02 / 0.73 | **out of memory** / 0.11 / 0.02 / 2.20 |
| edit → check | 0.14 / 0.12 / 0.17 / 0.30 | 0.77 / 0.13 / 0.53 / 0.41 | 3.33 / 0.47 / 2.15 / 1.10 |
| edit → build | 1.13 / 0.16 / 0.27 / 0.45 | **6.92** / 0.16 / 0.71 / 0.74 | **out of memory** / 0.43 / 3.00 / 2.24 |
| edit → test | 0.62 / 0.38 / 0.24 / 0.38 | 2.62 / 1.06 / 0.64 / 0.35 | 21.3 / 5.45 / 2.58 / 0.48 |
| interface → build | 1.68 / 0.18 / 0.26 / 0.42 | 9.81 / 0.18 / 0.77 / 0.75 | **out of memory** / 0.43 / 3.18 / 2.24 |

The default `mylang build` (ReleaseFast: LLVM `-O3` + LTO) at 50k: cold 369 s, edit →
build 95 s, interface → build 105 s. At 200k the Debug build fails inside 9 s with
`mylang: host failure: OutOfMemory` at 5.8–6.5 GB resident, under the compiler's default
8 GiB address-space ceiling; `check` needs 2.1 GB there.

Two readings. **Check is competitive at 10k and within 1.5–7× at 50k–200k**, so the
frontend's incremental work does its job for `check`. **Everything that produces a binary
scales with the project, not with the edit**: the no-op build grows from 1.0 s to 6.3 s and
then fails. Zig sets the bar — its self-hosted Debug backend builds 315k lines cold in
2.3 s — and Go rebuilds after an edit in under half a second at every size.

## 2. Where the build time goes

`--timings=json` for the 50k Debug project:

| Phase | No-op build | After a one-line body edit |
| --- | --- | --- |
| frontend | 8.18 s | 8.03 s |
| codegen | 1.17 s | 1.22 s |
| link | 0.04 s | 0.42 s |
| total | 9.49 s | 9.76 s |

`check main.my` on the same tree takes 0.12 s warm and 0.77–0.84 s after the edit. The
build frontend re-lowers and re-emits the whole program on every invocation — the README
says so ("ordinary whole-project builds still use the whole-program lowering path, and
incremental native linking remains open") — and holds all of it in memory at once, which
is what fails at 200k. The cold build pays roughly 100 ms per function object (4,560
functions at 50k), the same per-function process cost the 17 September scale probe found
(746 s for 4,803 objects).

## 3. Maintenance trials on the Lox codebase

The Lox interpreter (`bench/lox-20260922`) has two engines and a shared heap, ported to
mylang (4,182 non-blank lines), Go (4,974), Rust (5,455) and Zig (4,378) from one pinned
design. Two tasks, one fresh agent per language, graded by hidden cases plus the 487-script
conformance corpus in both engines and both GC modes:

- **break** — add a `break` statement to both engines: scanner, parser, resolver,
  tree interpreter, bytecode compiler (jump patching, popping locals, closing upvalues).
  22 hidden cases.
- **gcbug** — a planted bug: the collector no longer marks a closure's upvalues. The report
  gives one reproducer that crashes only under `--gc-stress` on the VM engine. 15 hidden
  cases. In every language the planted build crashed and the unplanted build agreed with
  the others on all 15 cases.

| Run | Hidden | Conformance | Wall min | Tool calls | ctx tokens | Min to first edit | Toolchain s |
| --- | --- | --- | --- | --- | --- | --- | --- |
| break mylang | 22/22 | all | 21.1 | 93 | 15.0 M | 7.7 | 138 |
| break Go | 22/22 | all | 13.7 | 78 | 10.2 M | 3.2 | 24 |
| break Rust | 22/22 | all | 16.9 | 86 | 13.6 M | 6.4 | 15 |
| break Zig | 22/22 | all | 21.6 | 93 | 14.5 M | 8.8 | 192 |
| gcbug mylang | 15/15 | all | 13.0 | 57 | 5.5 M | 2.9 | 123 |
| gcbug Go | 15/15 | all | 8.2 | 42 | 3.8 M | 2.7 | 24 |
| gcbug Rust | 15/15 | all | 8.9 | 54 | 5.2 M | 1.1 | 7 |
| gcbug Zig | 15/15 | all | 13.0 | 60 | 6.1 M | 1.6 | 254 |

(Toolchain seconds are on the E-cores and include every build, test and format call.)

**Reading.** mylang is level with Zig and 1.4–1.6× Go and Rust in wall time. It is not the
language that costs time — orientation before the first edit is comparable, and both mylang
agents' edits type-checked almost immediately (two compile errors in the whole break run).
The time goes to:

- **Release builds by default.** The mylang agents ran `mylang build`, i.e. LLVM `-O3` +
  LTO: 17–39 s per build after edits. Zig's agents chose `-Doptimize=ReleaseFast` from the
  port's `bench.json` and paid the same way (one 137 s build). Go and Rust used debug
  builds.
- **Tests that cannot run the program.** Both mylang agents wanted an end-to-end
  regression test through `driver.run_source` and could not write one: that function takes
  `clock: Option[Clock]`, passing `None` still charges the caller with `clock`
  (`E_EFFECT_BOUND`), and the test runner cannot supply a `Clock`. The gcbug agent spent a
  detour on `--cases` provider fixtures before abandoning it because a directory test run
  rejects `--cases`; the T4 agent in the pilot made two internal helpers `public` just to
  test them. The Go, Rust and Zig agents each added driver-level end-to-end tests.

Each agent's own ranking of what would have saved the most time put the capability/test
wall first or second (both mylang agents) and a bytecode disassembler near the top (first
for the mylang and Zig break agents, second for Go's — a port feature, not a language
one). The Go break agent's first wish was exhaustiveness checking over the token and AST
kinds so that the compiler lists every dispatch site; mylang already rejects a
non-exhaustive `match` over an enum or union (`E_INCOMPLETE_MATCH`), and the port's
tokens and AST are an enum and unions — an existing advantage for exactly this kind of
change, although the port's opcodes are integer constants that it does not cover.

## 4. Large-codebase tooling at 50k lines

| Query | Green | Red (type error in `m001`) |
| --- | --- | --- |
| `check main.my` (warm) | 0.12 s | 0.53 s, exit 1 |
| `context main.my --symbol=m060::f060_00` | 1.08 s, 7.5 KB | 0.53 s, 1.8 KB, still answers |
| `context … --symbol=m060.f060_00` (call-site spelling) | exit 2, "missing" | — |
| `tests-for main.my m060::f060_00` | 0.81 s, 1 KB | **exit 1, no answer** |
| `list-interfaces main.my` | 0.93 s, 505 KB | 0.48 s, 645 KB |
| `index-project main.my` | 1.11 s, **36 MB** | 0.57 s, 3.5 MB |
| `test main.my` cold / warm / after edit | 9.7 / 1.5 / 1.4 s | — |
| `test --affected --against HEAD` after edit | **8.0 s** (60 selected) | — |
| `check-session`, two checks | 1.0 s | — |

`context` and `tests-for` are the right shape — bounded, symbol-addressed, cheap. The rest
needs work before an agent would use it on a large codebase: an index an agent cannot
read, an affected-test selector that costs more than it saves, a `tests-for` that goes
silent exactly when an agent is mid-change, and symbol syntax that differs from how the
code spells the name. And discovery is the larger problem: across the ten
maintenance runs, three of them in mylang, the navigation commands were used zero times. Nothing in the
documentation the agents read, in `--help`'s first screen, or in diagnostics points at
them.

## 5. Churn: what a day of `main` costs code outside the repository

The Lox port was adapted to `main` 26f16e90 at about 00:00 UTC on 23 September by removing
1,024 call-site `mut` markers. To build it on `main` 35fcbc02 eleven hours later:

- the same 1,024 markers had to be put back, plus one aliasing rewrite for
  `E_MUTATION_OVERLAP`: 936 of 4,192 non-blank lines changed (22%);
- `driver_tests.my` (11 end-to-end tests) could not be recovered (the `Clock` wall of §3);
- `scripts/migrate_mut_arguments.py` reported "0 file(s) changed" for a relative path,
  then applied other files' diagnostics inside `main.my` (`driver.Emut ngine.TREE`),
  applied UTF-8 byte offsets to a `str`, skipped markers not in first position, and
  stopped after 64 rounds although the VM dispatch function reports one marker per check
  (fixed, §10);
- `check` rejects test entries (`E_MAIN`) and `test` rejects `--diagnostics=json`, so no
  tool can get structured diagnostics for a test file; `E_MUTATION_MARKER`'s JSON carries
  no `fix` field — the edit exists only in prose.

The markers were stripped and restored within twelve hours because `main` and
`perf/schematic-integration` enforced different rules on the same day. Six breaking
language changes landed between 17 and 22 September (print-to-Stream, Host capability,
`mutates` → `mut` parameters, call-site `mut`, derived effect ceilings, unused-capability
errors), each with its own script under `scripts/`. `main` took 45,292 added and 19,967
deleted lines of `.my` source in seven days.

## 6. Greenfield and onboarding (secondary)

Four greenfield tasks (word frequency over 10 MB, a recursive-descent calculator with
line/column errors, Dijkstra on 200k edges, quoted-CSV aggregation), each solved in mylang
and in Python; a fifth held-out task (access-log statistics) added with the primer.

| Task | mylang wall / calls / ctx | Python wall / calls / ctx | Ratio (wall) |
| --- | --- | --- | --- |
| T1 wordfreq | 11.8 min / 59 / 7.75 M | 3.7 / 17 / 1.01 M | 3.2 |
| T2 calc | 14.9 / 48 / 6.92 M | 6.3 / 18 / 1.30 M | 2.4 |
| T3 route | 13.5 / 59 / 7.97 M | 4.6 / 18 / 1.13 M | 2.9 |
| T5 csvstats | 15.7 / 52 / 8.41 M | 6.5 / 19 / 1.38 M | 2.4 |
| T6 logstats (held out) | 10.0 / 34 / 4.60 M | 5.1 / 18 / 1.21 M | 2.0 |

All ran every hidden case green. Geometric means over T1–T5: 2.7× wall time, 3.0× tool
calls, 6.5× context tokens. The pre-edit phase averaged 8.8 min against 2.6 min: ~70% of
the gap is reading (158–233 KB of docs per run); compiler time was 1.4% of wall time, and
the only repeated compile errors were layout traps (`test` needing a header, the module
name rule, `fmt` on a headered file, `[]` as an argument) — all fixed in §10.

**Primer experiment.** An 8.3 KB page ("mylang in one page — for Python programmers",
every snippet compile-verified) given to three more runs cut documentation read to
58–89 KB and context tokens by 17–52% (T2 3.3 M vs 6.9 M), but wall time moved both ways
(T2 11.7 vs 14.9 min; T5 17.3 vs 15.7 and T6 12.8 vs 10.0, both of which spent the saved
time on extra correctness and performance work). A primer lowers cost, not time.

In a large codebase this matters less: the maintenance agents read 6–23 KB of `docs/`
because the existing code and the port's `NOTES.md` taught them the language.

## 7. Silent wrong answers and the idiom ledger

`velocity/score.py` on 35fcbc02: **C1 = 21/67** CPython-oracle probes agree,
**C2_policy = 0**, **C3 = 42/73** rejections carry a structured fix or alternative. The
trials found a silent wrong answer the suite cannot reach, because the probe that would
reach it is rejected first: `strings.format_float` — the documented stand-in for the
rejected `f"{x:.2f}"` — printed `2.68` for 2.675 (C and Python: `2.67`), because
`2.675 * 100.0` rounds onto an exact half. Fixed in §10.

Cheap items the 17 September audit listed that are still open: f-string format specs,
`round(x, n)`, `**`, `set`, string ordering (`"a" < "b"`), `range` step, dict
comprehensions, generator arguments, `"ab" * 3`, chained comparisons. `ord`/`chr`,
tuples, the conditional expression and docstrings have landed since.

## 8. The language's own development loop

In seven days `main` took 403 commits. The repository has 282 branches and 102 worktrees;
24 branches with commits in the last three days hold 286 distinct commits not on `main`.
`docs/audits/` gained 113 dated documents since 15 September; recommendations that needed
no design (the build frontend reuse of §2 among them) have waited behind waves of new
rules and performance lanes. Two integration lines enforcing different language rules at
once is how the Lox port paid its migration twice.

## 9. Recommendations, ranked for large codebases

Each item names its evidence and a measurable acceptance rule on the ladder or the trials.

1. **Make every binary-producing command incremental.** `build`, `run` and `test` should
   reuse the checked facts `check` already reuses and lower/emit per function or per
   module, keyed on declaration identity, instead of re-lowering the program; link
   incrementally; never hold the whole lowered program in memory. Batch cold codegen
   (one QBE/assembler invocation per module, in parallel) instead of ~100 ms per function.
   *Evidence:* §1–2. *Accept when:* 50k no-op build ≤ 0.3 s and edit → build ≤ 1 s;
   200k builds under the default memory ceiling with edit → build ≤ 3 s; 50k cold ≤ 30 s.
   Put the ladder in the gate as a ratchet (`goal.json` already reserves `synthetic50k`
   and `synthetic500k`).
2. **Default `build` to a development build.** `mylang build` → Debug/QBE; `--release`
   selects LLVM `-O3` + LTO, as `cargo build --release` does. *Evidence:* §3 (17–39 s agent
   builds), 4 s LTO relink after a comment edit. *Accept when:* the maintenance trial's
   mylang toolchain seconds fall to Go/Rust's range (under 30 s per task).
3. **Let tests run capability-bearing code.** Discharge an effect when the capability
   argument is provably absent (`None` for `Option[Clock]`, extending the existing
   in-memory-capability discharge rule); provide deterministic test capabilities
   (`Clock.fixed`, `Entropy.seeded`, `Environment.of`, next to the existing
   `Filesystem.memory`); let `name_test.my` see `name`'s private declarations; allow
   `--cases` per file in directory runs. *Evidence:* §3, §5 — every mylang agent that
   touched the Lox VM hit this; the port lost its end-to-end tests. *Accept when:* the
   original `driver_tests.my` compiles and runs under `mylang test .` unchanged.
4. **Give large codebases a stability contract.** Ship `mylang fix` that applies every
   diagnostic's structured `fix` edit across a project (carry the edit in
   `E_MUTATION_MARKER`'s and similar diagnostics' JSON); pin a language edition in
   `mylang.json` so a project upgrades on its own schedule; require every breaking change
   to land with a `mylang fix` migration proven on the Lox, schematic and sexpr ports
   in the gate. *Evidence:* §5. *Accept when:* moving the Lox port across a breaking change
   is one command with zero hand edits.
5. **Make the navigation tools the obvious path, and fix their shapes.** Put a
   "working in a large project" block on `--help`'s first screen and in `mylang init`'s
   generated agent notes; make diagnostics offer `mylang context --at FILE:LINE`; bound
   `index-project` by default (query modes instead of a 36 MB dump); keep `tests-for`
   answering while the project is red, as `context` does; accept `module.name` wherever a
   symbol is taken; make `test --affected` cheaper than a cached full run. *Evidence:* §4.
   *Accept when:* in a rerun of the maintenance trials the mylang agents use at least one
   navigation command unprompted, and `--affected` after an edit costs ≤ 25% of a full run.
6. **Bring check latency at 200k under a second.** 3.3 s against Go 0.47 s and Zig 1.1 s.
   The 17 September scale probe found body reuse collapsing when `list[int]` first appears
   inside bodies (`interned-record`); the ladder's projects have exactly that shape.
   *Accept when:* 200k edit → check ≤ 1 s and test after edit ≤ 5 s.
7. **Close the cheap fidelity items.** Now that `format_float` rounds exactly, implement
   `{x:.2f}` format specs on it; add string ordering, `range` step, `**`, `round(x, n)`,
   `set`, dict comprehensions and generator arguments. *Evidence:* §7; each is a
   guaranteed repair round for any agent new to the language.
8. **Ship the primer and move internal documents out of `docs/`.** Put the verified
   one-page primer (`trials/devspeed-20260923/kit2/PRIMER.md`) at the top of the docs and
   under doctest; move `docs/audits/` and `docs/experiments/` (203 of 463 files) out of the
   user documentation. *Evidence:* §6 (−60–70% documentation read, −17–52% tokens).
9. **Adopt this audit's harness as the velocity loop's Lane A and B.** The trial kit
   (tasks, hidden cases, reference implementations, grader, toolchain shims, transcript
   statistics) is `velocity/solve.py` in all but name, and the scale ladder is the missing
   Lane B ratchet. Run both nightly with ≥ 3 samples per cell; keep one integration line
   so a downstream port never sees two rule sets in a day.

## 11. What this does not show

- **One run per cell, one model.** The maintenance differences (1.4–1.6× Go/Rust) are
  consistent across two tasks but not separable from run-to-run variance at this sample
  size; the scale ladder's differences (10–40× on builds, out-of-memory at 200k) are far
  outside it.
- **The generated projects are regular.** A chain of similar modules exaggerates nothing
  in the per-edit costs (each edit touches one body) but favours tools that parallelise
  per package; real codebases have wider graphs. The Lox trials are the realistic check,
  and they are 4–5k lines, not 50k.
- **Rust is one crate.** Real large Rust projects split into crates, which improves its
  edit → build; Go's numbers are already per-package.
- **Zig and Rust arms in the maintenance trials picked their own build profiles** (Zig
  chose ReleaseFast from `bench.json`); mylang's release default is its own choice, which
  is the point of recommendation 2.
- **Test counts differ by port.** The mylang port lost its 11 driver tests to the
  capability wall before the trials started; the other ports kept theirs.
